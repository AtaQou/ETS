1. ΔΙΟΡΘΩΣΕΙΣ ΚΑΙ ΠΡΟΣΘΗΚΕΣ ΓΙΑ ΤΟ ΚΕΦΑΛΑΙΟ 2

1.1 Τι λείπει από τη θεωρητική περιγραφή του eye tracking
Στο Κεφάλαιο 2 υπάρχει ήδη σωστή περιγραφή των fixations και saccades. Ωστόσο, για να στηρίξει καλύτερα τις τεχνικές αλλαγές του Κεφαλαίου 4, πρέπει να εξηγηθεί ότι η χρήση του βλέμματος ως input είναι πιο δύσκολη από τη χρήση του βλέμματος ως απλού μετρητικού εργαλείου. Σε ένα απλό πείραμα eye tracking, το βλέμμα καταγράφεται και αναλύεται μετά. Στο ETS, όμως, το βλέμμα ενεργοποιεί άμεσα λειτουργία μετάφρασης. Αυτό δημιουργεί το κλασικό πρόβλημα Midas touch: ο χρήστης μπορεί να κοιτάζει κάτι χωρίς να θέλει να το ενεργοποιήσει. Για τον λόγο αυτό έγιναν αλλαγές όπως baseGazeSamples, point/circle detection, hit radius, cooldown, translation output off και undesired translation feedback.

Προτεινόμενη προσθήκη στο Κεφάλαιο 2:
“Η αξιοποίηση του βλέμματος ως μηχανισμού εισόδου διαφοροποιείται από την απλή καταγραφή οφθαλμικών δεδομένων. Στην πρώτη περίπτωση, το σύστημα δεν παρατηρεί μόνο τη συμπεριφορά του χρήστη, αλλά λαμβάνει αποφάσεις με βάση αυτή. Η απόφαση αυτή ενέχει αβεβαιότητα, επειδή μια εστίαση δεν αντιστοιχεί πάντα σε πρόθεση ενεργοποίησης. Το πρόβλημα αυτό είναι γνωστό σε gaze-based interfaces ως Midas touch problem και απαιτεί μηχανισμούς φιλτραρίσματος, χρονικά κατώφλια, ανοχές σφάλματος και δυνατότητα ανατροφοδότησης από τον χρήστη.”

1.2 Τι λείπει από τη θεωρία για ανάγνωση σε μη μητρική γλώσσα
Το draft αναφέρει σωστά ότι η ανάγνωση σε μη μητρική γλώσσα δεν είναι απλή μετάφραση λέξεων. Χρειάζεται όμως να συνδεθεί περισσότερο με τη μετάβαση από isolated word translation σε context-aware translation. Αυτή η σύνδεση είναι κεντρική, γιατί δικαιολογεί γιατί δοκιμάστηκαν markers, Azure alignment και τελικά DeepL context.

Προτεινόμενη προσθήκη:
“Η σημασία μιας λέξης δεν είναι πάντοτε σταθερή ανεξάρτητα από το περιβάλλον της. Ιδίως σε κείμενα υψηλής δυσκολίας, η σωστή μετάφραση μιας λέξης εξαρτάται από τη συντακτική θέση, τη θεματική περιοχή και τα συμφραζόμενα της πρότασης. Επομένως, ένα σύστημα που μεταφράζει μόνο απομονωμένες λέξεις μπορεί να παράγει τεχνικά έγκυρα αλλά νοηματικά ακατάλληλα αποτελέσματα. Για τον λόγο αυτό, η παρούσα εργασία εξετάζει μορφές context-aware translation, στις οποίες η λέξη-στόχος μεταφράζεται με αξιοποίηση της πρότασης στην οποία ανήκει.”

1.3 Τι λείπει από τη θεωρία για ευχρηστία
Το Κεφάλαιο 2 περιγράφει την ευχρηστία, αλλά μπορεί να γίνει πιο συγκεκριμένο για τις ρυθμίσεις που προστέθηκαν. Οι sliders με αριθμητικό input, το show gaze cursor, το hover debug, το translation output off και το undesired feedback δεν είναι απλές UI προσθήκες. Είναι εργαλεία ελέγχου σε σύστημα που λειτουργεί με αβέβαιο input.

Προτεινόμενη προσθήκη:
“Σε εφαρμογές που βασίζονται σε οφθαλμική ιχνηλάτηση, η ευχρηστία δεν περιορίζεται στην αισθητική ή στην απλή πλοήγηση. Περιλαμβάνει τη δυνατότητα παραμετροποίησης της ευαισθησίας του συστήματος, την ορατότητα της εσωτερικής κατάστασης για σκοπούς διάγνωσης και τη δυνατότητα του χρήστη να διορθώνει ή να χαρακτηρίζει ανεπιθύμητες ενεργοποιήσεις. Οι ρυθμίσεις αυτές είναι απαραίτητες επειδή διαφορετικοί χρήστες, οθόνες και συνθήκες βαθμονόμησης παράγουν διαφορετικά επίπεδα θορύβου.”

1.4 Τι πρέπει να προστεθεί για ασφάλεια και μεταφραστικούς παρόχους
Στο θεωρητικό πλαίσιο μπορεί να μπει μικρή αναφορά ότι όταν μια εφαρμογή καλεί εξωτερικό μεταφραστικό API, υπάρχουν ζητήματα ασφάλειας, διαχείρισης μυστικών και ιδιωτικότητας. Αυτό δικαιολογεί τη μεταφορά της μετάφρασης στο backend και τη χρήση .env.

Προτεινόμενη προσθήκη:
“Η χρήση εξωτερικών μεταφραστικών υπηρεσιών εισάγει επιπλέον ζητήματα σχεδιασμού. Τα διαπιστευτήρια του παρόχου δεν πρέπει να εκτίθενται στον browser, ενώ οι κλήσεις μετάφρασης πρέπει να μπορούν να καταγράφονται, να ελέγχονται και να τροποποιούνται κεντρικά. Η μεταφορά της μεταφραστικής λογικής στο backend μειώνει την έκθεση μυστικών, διευκολύνει την αλλαγή παρόχου και επιτρέπει συνεπή logging πολιτική.”

2. ΔΙΟΡΘΩΣΕΙΣ ΚΑΙ ΠΡΟΣΘΗΚΕΣ ΓΙΑ ΤΟ ΚΕΦΑΛΑΙΟ 3

2.1 Το αρχικό ETS πρέπει να παρουσιαστεί ως λειτουργικό prototype
Η διατύπωση του Κεφαλαίου 3 είναι γενικά σωστή, αλλά μπορεί να γίνει πιο ακριβής. Το αρχικό ETS παρείχε βασική λειτουργία: φόρτωση PDF, OCR, word boxes, eye tracking, popup translation. Η παρούσα εργασία δεν ξεκινά από το μηδέν, αλλά ωριμάζει ένα prototype ώστε να χρησιμοποιηθεί σε πείραμα.

Προτεινόμενη διατύπωση:
“Το αρχικό ETS αποτέλεσε λειτουργικό prototype και όχι τελικό ερευνητικό εργαλείο. Η αξία του έγκειται στο ότι απέδειξε τη βασική τεχνική εφικτότητα: σύνδεση PDF viewer, OCR, eye tracker και μετάφρασης. Ωστόσο, για χρήση σε πειραματική διαδικασία πολλών συνεδριών απαιτούνταν μεγαλύτερη ακρίβεια, σταθερότητα, παραμετροποίηση, ασφάλεια και καταγραφή δεδομένων.”

2.2 Προβλήματα του παλαιού κώδικα που διορθώθηκαν
Τα προβλήματα που πρέπει να περιγραφούν στο Κεφάλαιο 3 ως περιορισμοί της αρχικής μορφής είναι:
- Γεωμετρική ασυνέπεια OCR/PDF/DOM/gaze. Το front-end δεν είχε πάντα τις πραγματικές OCR image dimensions και έκανε παραδοχές για ύψη, περιθώρια και κλίμακες σελίδας.
- Το overlay των word boxes και το hit-testing μπορούσαν να μην χρησιμοποιούν ακριβώς την ίδια γεωμετρία, άρα αυτό που έβλεπε ο ερευνητής δεν ταυτιζόταν απαραίτητα με αυτό που χρησιμοποιούσε η εφαρμογή.
- Το σύστημα δεν αντιδρούσε επαρκώς σε horizontal scroll, κάτι κρίσιμο σε υψηλό zoom.
- Δεν υπήρχε επαρκής εξήγηση/υποστήριξη για browser page zoom. Ο χρήστης μπορεί να αλλάξει όχι μόνο το zoom της εφαρμογής αλλά και το zoom του browser, το οποίο μεταβάλλει τα CSS pixels και άρα τη γεωμετρία του viewer.
- Η μετάφραση σε πρώιμες/πειραματικές μορφές δεν ήταν κεντρικοποιημένη στο backend, γεγονός που αύξανε τον κίνδυνο έκθεσης API key και δυσκόλευε logging/error handling.
- Οι ρυθμίσεις gaze δεν ήταν αρκετά παραμετροποιήσιμες ή μόνιμες ανά χρήστη.
- Δεν υπήρχε ολοκληρωμένο session-centric logging για translation events, settings changes, results, export και vocabulary.

2.3 Μορφολογικό πρόβλημα στο Κεφάλαιο 3
Στο draft η ενότητα 3.2 περιέχει πίνακα που έχει χαθεί μορφολογικά σε plain text μορφή, π.χ. “ΥποσύστημαΡόλοςΣημασία”. Στο τελικό κείμενο πρέπει να μετατραπεί σε σωστό πίνακα Word ή σε κανονικές παραγράφους. Δεν είναι τεχνικό λάθος περιεχομένου, αλλά μορφολογικό λάθος παρουσίασης.

Προτεινόμενη διόρθωση μορφής:
- Υποσύστημα προβολής PDF: εμφανίζει τις σελίδες, διαχειρίζεται zoom/scrolling και παρέχει DOM canvas ως γεωμετρικό σημείο αναφοράς.
- Υποσύστημα OCR και word boxes: εξάγει filtered words για gaze trigger και raw tokens για ανακατασκευή πρότασης.
- Υποσύστημα eye tracking: μετατρέπει normalized gaze samples σε viewport coordinates και εφαρμόζει hit-testing.
- Υποσύστημα μετάφρασης/δεδομένων: καλεί backend translation endpoints, εμφανίζει popup και καταγράφει translation events, settings changes και vocabulary.

3.2 Προσαρμογές Windows/Mac και αρχική υποδομή 2025
Στα commits Νοεμβρίου 2025 εμφανίζονται αλλαγές για mac setup, requirements, database initialization, show boxes και custom zoom στο UI. Το πειραματικό περιβάλλον πρέπει να περιγραφεί ως Windows.

3.3 Διόρθωση word boxes και debug overlay
Στα commits γύρω από το PR “explain-box-creation-and-frontend-retrieval” εμφανίζονται οι αλλαγές:

- Align overlays using server page dimensions.
- Fix overlay recalculation and type errors.
- Document overlay box parity.
- Add hover-to-translate debug option.
Αυτή η ομάδα αλλαγών είναι βασική για το Κεφάλαιο 4, επειδή λύνει το πρόβλημα ότι τα OCR boxes δεν ευθυγραμμίζονταν αξιόπιστα με το πραγματικό rendered PDF.

3.4 Παραμετροποίηση base gaze samples
Το branch codex/add-custom-base-time-setting-for-eye-tracker πρόσθεσε configurable base gaze samples, μετά έγινε revert και στη συνέχεια η λειτουργία επανήλθε χειροκίνητα/βελτιωμένα στο commit 5dad730. Στο κείμενο πρέπει να παρουσιαστεί ως τελική δυνατότητα παραμετροποίησης του χρόνου ενεργοποίησης μετάφρασης. Δεν χρειάζεται να αναφερθεί το revert, εκτός αν θέλεις να δείξεις διαδικασία ανάπτυξης. Για διπλωματική αρκεί ότι το αρχικό σταθερό threshold αντικαταστάθηκε από ρύθμιση χρήστη.

3.5 Sentence translation και ενδιάμεση marker-based ροή
Τα commits Φεβρουαρίου/Μαρτίου 2026 πρόσθεσαν sentence translation και αργότερα στο test-mac δοκιμάστηκε contextually correct μετάφραση με markers. Αυτή ήταν ενδιάμεση προσέγγιση: η λέξη επισημαινόταν μέσα στην πρόταση με ειδικούς markers, το πλήρες κείμενο μεταφραζόταν και μετά επιχειρούνταν εξαγωγή του τμήματος ανάμεσα στους markers. Η προσέγγιση είχε θεωρητικό πλεονέκτημα, επειδή έδινε συμφραζόμενα στον πάροχο, αλλά είχε σοβαρό μειονέκτημα: οι μεταφραστικοί πάροχοι δεν εγγυώνται ότι θα διατηρήσουν markers αναλλοίωτους. Επίσης σε εκείνη τη φάση υπήρχε λογική μετάφρασης στο front-end, που δεν είναι ασφαλής για API keys.

3.6 Βελτιώσεις gaze visualizer, mapping και circle mode
Τα commits Μαρτίου 2026 πρόσθεσαν gaze visualizer, custom gaze fixer και circle uncertainty mode. Αυτό πρέπει να παρουσιαστεί ως μετάβαση από αυστηρό point-based matching σε πιο ανθεκτική ανίχνευση, κατάλληλη για πραγματικές συνθήκες βαθμονόμησης. Το Point mode κρατήθηκε ως legacy/strict επιλογή, ενώ το Circle mode έγινε πιο πρακτικό default.

3.7 Horizontal scroll recalculation και popup μετά την επιστροφή μετάφρασης
Το commit “horizontal scroll box recalculation” πρόσθεσε την παρακολούθηση scrollLeft. Αυτό είναι σημαντικό σε υψηλό zoom, όπου ο χρήστης δεν κινείται μόνο κάθετα αλλά και οριζόντια. Το commit “bubble shows only after translation return” διόρθωσε το φαινόμενο κενό popup: το popup εμφανίζεται μόνο όταν υπάρχει non-empty translated text.

4. ΠΡΟΒΛΗΜΑΤΑ ΤΟΥ ΠΑΛΑΙΟΥ ΚΩΔΙΚΑ ΠΟΥ ΔΙΟΡΘΩΘΗΚΑΝ

4.1 Πρόβλημα: ασυμφωνία OCR boxes και PDF canvas
Πριν τις αλλαγές, το backend παρήγαγε OCR boxes σε συντεταγμένες εικόνας OCR, ενώ το front-end εμφάνιζε PDF σε canvas με δικές του rendered διαστάσεις. Αν το front-end δεν γνώριζε τις πραγματικές OCR image dimensions, έπρεπε να υποθέτει κλίμακες ή σταθερά offsets. Αυτή η υπόθεση έσπαγε σε διαφορετικό zoom, διαφορετικό browser rendering ή διαφορετική διάσταση σελίδας.

Τι διορθώθηκε:
Το backend επιστρέφει πλέον για κάθε σελίδα width και height της επεξεργασμένης OCR εικόνας. Η συνάρτηση calculateScaledPositions στο front-end παίρνει το raw OCR box, βρίσκει το πραγματικό DOM canvas της σελίδας με βάση data-page-number, παίρνει getBoundingClientRect και υπολογίζει scaleX και scaleY. Έτσι μετατρέπει τις OCR συντεταγμένες σε viewport coordinates.

Γιατί ευνοεί:
Η μετάφραση ενεργοποιείται στη λέξη που βλέπει πραγματικά ο χρήστης, όχι σε λέξη που προκύπτει από λανθασμένη κλίμακα. Επίσης το debug overlay γίνεται αξιόπιστο, γιατί δείχνει τα ίδια boxes που χρησιμοποιεί το hit-testing.

Πιθανό αρνητικό/όριο:
Η σωστή λειτουργία εξαρτάται από το να έχει ήδη renderαριστεί το DOM canvas. Για αυτό υπάρχει ανάγκη να γίνεται recalculation μετά από rendering, zoom και scroll. Αν το canvas δεν υπάρχει προσωρινά, η συνάρτηση επιστρέφει μηδενικές συντεταγμένες.

4.2 Πρόβλημα: overlay και hit-testing δεν ήταν εγγυημένα ίδιο σύστημα
Πριν τις αλλαγές, υπήρχε κίνδυνος το overlay να χρησιμοποιεί μία γεωμετρία και το TextBox/hit-testing άλλη. Αυτό είναι επικίνδυνο για debugging, γιατί ο ερευνητής μπορεί να βλέπει σωστά κουτιά αλλά η εφαρμογή να αποφασίζει με άλλες θέσεις.

Τι διορθώθηκε:
Το WordBoxesOverlay και το TextBox χρησιμοποιούν την ίδια calculateScaledPositions και τα ίδια wordPositions. Άρα η οπτική ένδειξη και η πραγματική ανίχνευση βασίζονται στην ίδια χαρτογράφηση.

Γιατί ευνοεί:
Ο ερευνητής μπορεί να χρησιμοποιήσει το overlay ως πραγματική διάγνωση και όχι ως περίπου οπτικοποίηση. Αυτό μειώνει τον χρόνο debugging και αυξάνει την εμπιστοσύνη στο πείραμα.

4.3 Πρόβλημα: vertical-only recalculation
Πριν, η λογική επανυπολογισμού συντεταγμένων λάμβανε υπόψη κυρίως το vertical scroll. Όμως σε υψηλό zoom το PDF συχνά απαιτεί horizontal scroll. Αν ο χρήστης μετακινηθεί οριζόντια και τα boxes δεν επανυπολογιστούν, τα boxes και το hit-testing μένουν σε παλιά θέση.

Τι διορθώθηκε:
Το FileViewer αποθηκεύει πλέον και scrollLeft, όχι μόνο scrollTop. Το WordBoxesOverlay και το TextBox έχουν dependencies τόσο σε scrollTop όσο και σε scrollLeft, ώστε να επανυπολογίζουν τις οθονικές θέσεις των λέξεων όταν ο χρήστης κινείται σε οποιαδήποτε κατεύθυνση.

Γιατί ευνοεί:
Η ανίχνευση παραμένει σωστή σε μεγάλα zoom levels, όπου ο χρήστης βλέπει μόνο τμήμα της σελίδας και μετακινείται πλάγια. Αυτό είναι κρίσιμο για πειραματική σταθερότητα, γιατί διαφορετικοί χρήστες μπορεί να επιλέξουν διαφορετικό zoom.

4.4 Πρόβλημα: zoom εφαρμογής και browser zoom
Το αρχικό σύστημα αντιμετώπιζε κυρίως το zoom της εφαρμογής/PDF. Όμως ο browser έχει και δικό του page zoom, το οποίο αλλάζει το μέγεθος των CSS pixels και τη γεωμετρία που βλέπει ο χρήστης. Αν η εφαρμογή βασιστεί μόνο σε αριθμητικό zoom setting, μπορεί να αγνοήσει τη μεταβολή που εισάγει ο browser.

Τι διορθώθηκε:
Η calculateScaledPositions δεν βασίζεται μόνο στο αποθηκευμένο zoom. Διαβάζει το πραγματικό getBoundingClientRect του canvas. Το getBoundingClientRect επιστρέφει τις πραγματικές CSS διαστάσεις και θέσεις όπως εμφανίζονται στο viewport μετά από app zoom, browser zoom, layout και scroll. Έτσι η εφαρμογή χαρτογραφεί boxes στο ίδιο σύστημα συντεταγμένων που χρησιμοποιείται από clientX/clientY και από το gaze mapping.

Γιατί ευνοεί:
Η γεωμετρική αντιστοίχιση γίνεται πιο ανθεκτική σε μεταβολές περιβάλλοντος. Δεν χρειάζεται να προβλέψουμε θεωρητικά όλα τα zoom/scale factors, γιατί λαμβάνουμε την τελική rendered γεωμετρία από το DOM.

Πιθανό όριο:
Αν ο browser zoom αλλάξει πολύ απότομα, απαιτείται rerender/recalculation. Το σύστημα το χειρίζεται έμμεσα μέσω DOM rect και resize/scroll/render events, αλλά καλό είναι να αναφερθεί ότι η γεωμετρία εξαρτάται από το τελικό rendered canvas.

4.5 Πρόβλημα: ανεπαρκής έλεγχος trigger από τον χρήστη
Το αρχικό σύστημα είχε πιο σταθερές τιμές για τον χρόνο ενεργοποίησης. Όμως οι χρήστες δεν έχουν ίδιο ρυθμό ανάγνωσης ούτε ίδιο calibration accuracy.

Τι διορθώθηκε:
Προστέθηκε baseGazeSamples με slider και numeric input, αρχικά μέχρι 600 και στη συνέχεια μέχρι 1200 samples. Προστέθηκαν επίσης gazeDetectionMode, gazeHitRadiusPx, gazeYOffsetPx, gazeXOffsetPx και gazeMappingMode.

Γιατί ευνοεί:
Ο ερευνητής μπορεί να προσαρμόσει την ευαισθησία ανά συμμετέχοντα. Ένας χρήστης με πολλά false positives μπορεί να χρειάζεται μεγαλύτερο base gaze time ή μικρότερο hit radius. Ένας χρήστης με offset μπορεί να χρειάζεται X/Y correction.

Πιθανό αρνητικό:
Η αυξημένη παραμετροποίηση κάνει το σύστημα πιο ισχυρό αλλά και πιο σύνθετο. Για αυτό χρειάζεται καταγραφή των ρυθμίσεων, ώστε οι αλλαγές να είναι ερμηνεύσιμες μετά το πείραμα.

4.6 Πρόβλημα: gaze mapping σε διαφορετικά παράθυρα/οθόνες
Το Tobii δίνει normalized gaze coordinates σε σχέση με την οθόνη/διάταξη, ενώ το PDF βρίσκεται μέσα σε browser viewport. Σε fullscreen, non-fullscreen ή extended display setup, μπορεί να υπάρχει systematic offset.

Τι διορθώθηκε:
Προστέθηκαν mapping modes auto, viewport και screenAdjusted. Το screenAdjusted προσπαθεί να μετατρέψει absolute screen coordinates σε viewport coordinates λαμβάνοντας υπόψη window.screenX/screenY, outer/inner dimensions και browser chrome. Το viewport mode χαρτογραφεί απευθείας normalized coordinates στο viewport. Το auto επιλέγει πιο ανθεκτικά ανάλογα με overflow. Προστέθηκαν X/Y offsets για χειροκίνητη βαθμονόμηση.

Γιατί ευνοεί:
Η εφαρμογή μπορεί να χρησιμοποιηθεί σε setup όπου ο χρήστης βρίσκεται σε μία οθόνη και ο ερευνητής σε άλλη. Το X offset λύνει πρακτικά προβλήματα όπου το gaze “κλείδωνε” προς τη δεξιά πλευρά σε extended display.

Πιθανό αρνητικό:
Η λύση παραμένει πρακτική/εμπειρική, επειδή οι browsers και τα λειτουργικά συστήματα δεν δίνουν πάντα πλήρως αξιόπιστη γεωμετρία για browser chrome και multi-monitor setups. Χρειάζεται calibration/δοκιμή πριν από κάθε πειραματική συνεδρία.

4.7 Πρόβλημα: αυστηρό point-based matching
Η αρχική αυστηρή λογική απαιτούσε τα gaze samples να πέφτουν πρακτικά πάνω στο κουτί της λέξης. Σε πραγματικές συνθήκες, ακόμη και καλό eye tracking έχει θόρυβο.

Τι διορθώθηκε:
Προστέθηκε Circle mode. Αντί να απαιτεί πλήρη ταύτιση, ορίζει ακτίνα αβεβαιότητας γύρω από κάθε gaze point και αξιολογεί υποψήφιες λέξεις με hit ratio και distance-based scoring. Για performance, γίνεται candidate preselection στις κοντινότερες λέξεις και throttle στον ρυθμό υπολογισμών.

Γιατί ευνοεί:
Μειώνονται τα false negatives όταν το βλέμμα είναι κοντά στη λέξη αλλά όχι ακριβώς μέσα στο box. Αυτό κάνει το σύστημα πιο πρακτικό σε πραγματικό πείραμα.

Πιθανό αρνητικό:
Αν η ακτίνα είναι υπερβολικά μεγάλη, αυξάνεται ο κίνδυνος false positives, ειδικά σε πυκνό κείμενο. Για αυτό διατηρήθηκε και Point mode ως strict επιλογή.

4.8 Πρόβλημα: μετάφραση χωρίς αρκετά συμφραζόμενα
Η απομονωμένη μετάφραση λέξης μπορεί να είναι σημασιολογικά λάθος. Π.χ. μια αγγλική λέξη με πολλές σημασίες μπορεί να μεταφραστεί διαφορετικά ανάλογα με την πρόταση.

Τι διορθώθηκε:
Δοκιμάστηκαν τρεις διαδρομές:
- Marker-based Google/contextual approach στο test-mac.
- Azure alignment στο test2.
- DeepL context στο τελικό deepltest.
Η τελική λύση DeepL στο word mode στέλνει ως text τη λέξη/φράση που εντοπίστηκε και ως context την πρόταση. Στο sentence mode στέλνει ως text ολόκληρη την πρόταση.

Γιατί ευνοεί:
Το σύστημα προσφέρει context-aware μετάφραση χωρίς να χρειάζεται να εκθέτει API keys στο front-end και χωρίς να απαιτεί marker parsing. Η ποιότητα αναμένεται καλύτερη από απομονωμένη μετάφραση, ειδικά σε πολυσημία.

Πιθανό αρνητικό:
Η DeepL τελική υλοποίηση δεν παρέχει ρητό source-target alignment όπως η Azure. Άρα δεν είναι deterministic με την ίδια έννοια. Η σωστή λέξη καθορίζεται πριν από την κλήση API μέσω OCR focusBox, όχι μετά μέσω extraction από πλήρη translated sentence.

4.9 Πρόβλημα: κενό ή flickering translation popup
Πριν, το popup μπορούσε να εμφανιστεί αμέσως με το trigger, πριν επιστρέψει η μετάφραση. Αυτό δημιουργούσε οπτικά κενό bubble ή flicker.

Τι διορθώθηκε:
Στο TextBox το popup εμφανίζεται μόνο όταν shouldTranslate είναι true, το translationOutputMode είναι on και το translation.trim().length είναι μεγαλύτερο από 0.

Γιατί ευνοεί:
Η εμπειρία είναι πιο καθαρή. Ο χρήστης δεν βλέπει άδειο στοιχείο και δεν αποσπάται από ενδιάμεση κατάσταση φόρτωσης.

4.10 Πρόβλημα: μη διάκριση χρήσιμων και ανεπιθύμητων μεταφράσεων
Σε gaze-based σύστημα, κάποιες μεταφράσεις μπορεί να ενεργοποιηθούν επειδή ο χρήστης απλώς καθυστέρησε πάνω σε μια λέξη, όχι επειδή χρειαζόταν βοήθεια.

Τι διορθώθηκε:
Προστέθηκε μικρό control στο translation popup για undesired translation. Όταν ο χρήστης το πατά, το event παραμένει στα Results με flag isUndesired, αλλά εξαιρείται από το Vocabulary.

Γιατί ευνοεί:
Η πειραματική καταγραφή δεν χάνει δεδομένα, αλλά το λεξιλόγιο δεν “μολύνεται” από λέξεις που ο χρήστης δεν θεωρεί πραγματικά άγνωστες ή χρήσιμες.

Πιθανό αρνητικό:
Προστίθεται μικρό βάρος αλληλεπίδρασης στον χρήστη. Αν ο χρήστης δεν πατά συστηματικά το κουμπί, το flag δεν αποτυπώνει όλες τις ανεπιθύμητες ενεργοποιήσεις.

5. ΤΕΛΙΚΗ ΛΕΙΤΟΥΡΓΙΑ ΣΥΣΤΗΜΑΤΟΣ ΜΕΤΑ ΤΙΣ ΑΛΛΑΓΕΣ

5.1 Φόρτωση PDF και εξαγωγή OCR δεδομένων
Όταν ο χρήστης επιλέξει έγγραφο, το backend διαβάζει το PDF και μετατρέπει κάθε σελίδα σε εικόνα μέσω pdf2image. Στη συνέχεια το Tesseract εξάγει tokens και boxes. Η τελική δομή ανά σελίδα περιέχει:
- page: αριθμός σελίδας.
- width/height: πραγματικές διαστάσεις της επεξεργασμένης εικόνας OCR.
- data: φιλτραρισμένες λέξεις κατάλληλες για gaze trigger.
- tokensAll: όλα τα raw OCR tokens, μαζί με punctuation, stopwords, confidence, box και block/paragraph/line metadata.

Ο διαχωρισμός data και tokensAll είναι σημαντικός. Η λίστα data πρέπει να είναι καθαρή, ώστε το gaze trigger να μη στοχεύει σημεία στίξης, URLs, πολύ μικρές λέξεις ή stopwords. Η λίστα tokensAll πρέπει να κρατά περισσότερη πληροφορία, επειδή η πρόταση δεν μπορεί να ανακατασκευαστεί σωστά αν αφαιρεθεί η στίξη.

5.2 Χαρτογράφηση OCR boxes στην οθόνη
Το front-end λαμβάνει τα wordPositions μέσω WordPositionsProvider. Για την τρέχουσα σελίδα, το TextBox παίρνει κάθε OCR box και καλεί calculateScaledPositions. Η συνάρτηση βρίσκει το wrapper με data-page-number, εντοπίζει το canvas της σελίδας και διαβάζει getBoundingClientRect. Μετά υπολογίζει:
- scaleX = rendered canvas width / OCR image width.
- scaleY = rendered canvas height / OCR image height.
- xPrime = canvas left + OCR x * scaleX.
- yPrime = canvas top + OCR y * scaleY.
- wPrime = OCR w * scaleX.
- hPrime = OCR h * scaleY.

Το αποτέλεσμα είναι viewport/client coordinates. Αυτό σημαίνει ότι μπορεί να συγκριθεί άμεσα με mouse event coordinates και με gaze coordinates μετά το mapping.

5.3 Recalculation σε zoom, vertical scroll, horizontal scroll και browser zoom
Το σύστημα επανυπολογίζει τις θέσεις όταν αλλάζει η τρέχουσα σελίδα, όταν αλλάζουν τα δεδομένα OCR, όταν γίνει mount η σελίδα, και όταν αλλάζουν scrollTop ή scrollLeft. Σε app zoom, το react-pdf Page rerenderάρεται με νέο scale και το canvas αποκτά νέες rendered διαστάσεις. Σε browser zoom, το getBoundingClientRect επιστρέφει διαφορετικές CSS διαστάσεις, άρα η κλιμάκωση προσαρμόζεται στο τελικό αποτέλεσμα που βλέπει ο χρήστης.

Αυτό είναι σημαντικό επειδή το hit-testing δεν πρέπει να βασίζεται σε θεωρητικό zoom αλλά στην πραγματική οπτική θέση της λέξης. Αν ο χρήστης κάνει zoom στο PDF ή στο browser, ή αν μετακινηθεί οριζόντια/κάθετα, οι λέξεις αλλάζουν θέση στο viewport. Χωρίς recalculation, το gaze θα συγκρινόταν με παλιές συντεταγμένες και θα επέστρεφε λάθος λέξη.

5.4 Κοινή ροή gaze και hover debug
Το hover debug δεν αποτελεί δεύτερο σύστημα μετάφρασης. Χρησιμοποιεί τα ίδια wordsScreenPositions που χρησιμοποιεί το eye tracker. Αν ο κέρσορας βρίσκεται μέσα σε box, ορίζεται currentWord και ενεργοποιείται shouldTranslate. Αν ο κέρσορας βγει από box, απενεργοποιείται. Αυτό δίνει στον ερευνητή γρήγορο τρόπο να ελέγξει αν η μετάφραση, η ανάκτηση πρότασης και το popup λειτουργούν, χωρίς να απαιτείται ενεργό Tobii.

Στη διπλωματική πρέπει να τονιστεί ότι το hover debug έγινε για ανάπτυξη/έλεγχο και όχι ως πειραματική λειτουργία συμμετέχοντα.

5.5 Gaze pipeline
Τα δεδομένα Tobii φτάνουν ως normalized gaze samples. Το front-end τα μετατρέπει σε viewport coordinates με createGazePointMapper. Ανάλογα με το gazeMappingMode:
- viewport: normalized x/y πολλαπλασιάζονται με το viewport width/height.
- screenAdjusted: normalized x/y μετατρέπονται σε absolute screen pixels και μετά αφαιρείται η θέση του browser viewport στην οθόνη.
- auto: το σύστημα συγκρίνει ποια χαρτογράφηση δίνει μικρότερο overflow εκτός viewport και επιλέγει πιο λογική τιμή.

Μετά εφαρμόζονται gazeXOffsetPx και gazeYOffsetPx. Αυτά είναι χειροκίνητες διορθώσεις για setup-specific αποκλίσεις. Το Y offset πλέον μπορεί να είναι θετικό ή αρνητικό, ενώ το X offset βοηθά σε extended display setups.

5.6 Detection modes
Στο Point mode, το σύστημα απαιτεί όλα τα σχετικά gaze samples να βρίσκονται μέσα στο box της λέξης. Αυτό είναι αυστηρό και κατάλληλο για debugging ή πολύ καλή βαθμονόμηση.

Στο Circle mode, το σύστημα θεωρεί ότι γύρω από κάθε gaze point υπάρχει ακτίνα αβεβαιότητας. Για κάθε υποψήφια λέξη υπολογίζεται πόσα gaze points βρίσκονται εντός ακτίνας από το box και πόσο κοντά είναι στο box/κέντρο της λέξης. Η λέξη με καλύτερο score επιλέγεται. Για να μη γίνεται ακριβός έλεγχος σε όλες τις λέξεις συνεχώς, γίνεται αρχικά candidate preselection στις πιο κοντινές λέξεις και το detection τρέχει throttled.

5.7 Τελική DeepL μεταφραστική ροή
Η τελική ροή έχει ως εξής:
1. Το TextBox έχει ήδη currentWord από gaze ή hover. Το currentWord περιέχει word, wordCoords και sourceBox.
2. Το sourceBox είναι το OCR box της λέξης στην εικόνα OCR, όχι απλώς το box στην οθόνη.
3. Το front-end καλεί /api/sentence-from-focus με docID, userID, page και focusBox.
4. Το backend βρίσκει το OCR token που έχει τη μεγαλύτερη επικάλυψη με το focusBox. Αυτό είναι το κρίσιμο βήμα με το οποίο καθορίζεται ποια λέξη εννοεί το σύστημα.
5. Το backend περιορίζει την αναζήτηση στο ίδιο block/paragraph όταν είναι δυνατό, και κόβει πρόταση από boundary σε boundary με βάση punctuation.
6. Το backend επιστρέφει sentence, matchedToken και matchedTokenRaw.
7. Αν το mode είναι word, το front-end στέλνει στο /api/translate text = matchedToken και context = sentence.
8. Αν το mode είναι sentence, το front-end στέλνει text = sentence και context κενό.
9. Το backend καλεί DeepL με το API key από server-side περιβάλλον και επιστρέφει translation, provider=deepl, mode και contextUsed.
10. Το front-end εμφανίζει popup μόνο αν υπάρχει non-empty translation και translationOutputMode είναι on.
11. Το translation event καταγράφεται με sessionID, docID, page, sourceText, translatedText, provider, mode, output mode, settings snapshot και isUndesired=false.

Σημαντική διόρθωση για τη διπλωματική:
Στην τελική DeepL ροή, όταν είμαστε σε word mode, δεν στέλνουμε ολόκληρη την πρόταση ως κύριο text και μετά ψάχνουμε ποια λέξη επέστρεψε. Στέλνουμε τη στοχευμένη λέξη/φράση ως text και την πρόταση ως context. Άρα η “σωστή λέξη” καθορίζεται πριν την κλήση DeepL, από το OCR focusBox και το overlap matching. Η πρόταση χρησιμοποιείται για σημασιολογική καθοδήγηση της μετάφρασης, όχι για extraction target span.

5.8 Πώς λειτουργούσε η Azure πειραματική ροή και γιατί δεν είναι η τελική
Στο Azure branch test2 η ιδέα ήταν διαφορετική. Εκεί το σύστημα έστελνε την πρόταση ως κύριο κείμενο και κρατούσε focusSpan, δηλαδή character offsets της λέξης-στόχου μέσα στην αρχική πρόταση. Το Azure Translator επέστρεφε alignment πληροφορία source-target. Το backend χαρτογραφούσε το sourceSpan στο αντίστοιχο targetSpan και μπορούσε να εξαγάγει μόνο το μεταφρασμένο τμήμα που αντιστοιχούσε στη λέξη.

Πλεονέκτημα Azure alignment:
Η διαδικασία ήταν πιο deterministic σε επίπεδο substring extraction. Μπορούσε να απαντήσει στο ερώτημα “ποιο τμήμα της μεταφρασμένης πρότασης αντιστοιχεί στη λέξη που κοίταξε ο χρήστης”.

Μειονέκτημα Azure alignment:
Η ποιότητα και η φυσικότητα της μετάφρασης δεν ήταν απαραίτητα καλύτερη από DeepL. Επίσης το alignment προσθέτει πολυπλοκότητα και μπορεί να γίνει εύθραυστο όταν το OCR έχει λάθη, όταν η μετάφραση αλλάζει τη σειρά των λέξεων ή όταν μία λέξη αποδίδεται ως φράση.

Γιατί μετακινήθηκε η τελική λύση σε DeepL:
Το DeepL επιλέχθηκε στο τελικό branch με λογική quality over latency. Δηλαδή δόθηκε προτεραιότητα στη φυσικότητα και στη συμφραζομενική ποιότητα της μετάφρασης. Η τελική προσέγγιση χάνει το ρητό alignment, αλλά απλοποιεί τη ροή: στο word mode μεταφράζεται η λέξη με sentence context, ενώ στο sentence mode μεταφράζεται η πρόταση.

5.9 Marker-based ροή και γιατί δεν κρατήθηκε
Η marker-based ροή δοκίμασε να βάλει ειδικούς markers γύρω από τη λέξη μέσα στην πρόταση, να μεταφράσει την πρόταση και μετά να εξαγάγει το κομμάτι ανάμεσα στους markers. Η ιδέα ήταν καλή επειδή επέτρεπε πλήρες context και προσπάθεια επιστροφής μόνο της λέξης.

Δεν κρατήθηκε ως τελική λύση γιατί:
- Δεν υπάρχει εγγύηση ότι ο μεταφραστικός πάροχος θα διατηρήσει τους markers.
- Οι markers μπορεί να μετακινηθούν, να αλλοιωθούν ή να επηρεάσουν τη μετάφραση.
- Χρειάζονται fallbacks και καθαρισμοί artifacts.
- Σε εκείνη τη φάση υπήρχε κλήση API από το front-end, άρα αυξημένος κίνδυνος έκθεσης credentials.

Στη διπλωματική μπορεί να παρουσιαστεί ως ενδιάμεσο πείραμα που οδήγησε στη διαπίστωση ότι χρειάζεται backend-controlled και πιο καθαρή context-aware ροή.

5.10 Session-centric logging
Η τελική εφαρμογή έχει πειραματικό logging οργανωμένο γύρω από sessions. Το session ξεκινά όταν συνδέεται ο eye tracker και κλείνει όταν αποσυνδέεται ή γίνεται logout. Επίσης σε ορισμένες αλλαγές που επηρεάζουν την πειραματική κατάσταση, όπως αλλαγές settings/output mode/document, το σύστημα μπορεί να κλείνει παλιό session και να ξεκινά νέο, ώστε τα δεδομένα να παραμένουν καθαρά.

Καταγράφονται:
- user_sessions: sessionID, userID, tracker metadata, startedAt, endedAt, startSettings.
- translation_events: κάθε επιτυχής μετάφραση με sourceText, translatedText, provider, mode, doc/page, settings snapshot, output mode και undesired flag.
- translation_stats: συγκεντρωτική συχνότητα χρήσεων ανά όρο/session.
- settings_change_events: τι άλλαξε, παλιές/νέες τιμές και timestamp.

Αυτό επιτρέπει ανάλυση όχι μόνο του τελικού αποτελέσματος αλλά και της συμπεριφοράς κατά τη διάρκεια της ανάγνωσης.

5.11 Results UI
Το Results UI επιτρέπει επιλογή χρήστη και session, και εμφανίζει στοιχεία session, αρχικές ρυθμίσεις, PDF context και timeline. Το timeline ενώνει translations και settings changes. Αυτό είναι σημαντικό γιατί μια αλλαγή ρύθμισης μπορεί να εξηγεί μεταβολή στη συμπεριφορά του χρήστη. Για παράδειγμα, αν ο ερευνητής αυξήσει baseGazeSamples στη μέση μιας συνεδρίας, μετά μπορεί να ελέγξει αν μειώθηκαν οι ανεπιθύμητες μεταφράσεις.

5.12 Vocabulary
Το Vocabulary δεν είναι δεύτερη ανεξάρτητη βάση. Παράγεται από τα translation_events, με απο-διπλοποίηση ανά χρήστη, translation mode και sourceText. Εξαιρεί μεταφράσεις με translationOutputMode=off και isUndesired=1. Επίσης εμφανίζει docName και επιτρέπει φίλτρο ανά PDF.

Γιατί ευνοεί:
Υπάρχει single source of truth. Τα Results και Vocabulary προέρχονται από το ίδιο logging pipeline, άρα δεν υπάρχει ασυνέπεια μεταξύ “τι συνέβη” και “τι αποθηκεύτηκε ως λεξιλόγιο”.

Πιθανό αρνητικό:
Αν μια χρήσιμη μετάφραση δεν καταγραφεί λόγω τεχνικού σφάλματος ή επειδή δεν υπάρχει ενεργό sessionID, δεν θα εμφανιστεί ούτε στο Vocabulary. Άρα η ποιότητα του Vocabulary εξαρτάται από την ποιότητα του logging.

5.13 Translation output off
Η λειτουργία Translation output off επιτρέπει το σύστημα να συνεχίζει να ανιχνεύει και να καταγράφει μεταφραστικά events, αλλά να μην εμφανίζει popup στον χρήστη. Αυτό είναι χρήσιμο ως control condition ή ως τρόπος συλλογής gaze-triggered μεταφραστικών αναγκών χωρίς άμεση υποβοήθηση.

Πλεονέκτημα:
Δίνει δυνατότητα σύγκρισης συνθηκών με και χωρίς ορατή μετάφραση.

Μειονέκτημα:
Ο χρήστης δεν λαμβάνει βοήθεια εκείνη τη στιγμή, άρα δεν είναι κατάλληλο για κανονική χρήση υποστήριξης. Επίσης πρέπει να εξηγηθεί στους συμμετέχοντες/στη μεθοδολογία.

4. Επεκτάσεις και τεχνικές αλλαγές του συστήματος

4.1 Προσαρμογή περιβάλλοντος ανάπτυξης και υποδομής
Η πρώτη κατηγορία αλλαγών αφορούσε την προσαρμογή της εφαρμογής ώστε να μπορεί να αναπτυχθεί και να ελεγχθεί με μεγαλύτερη σταθερότητα σε διαφορετικά περιβάλλοντα. Πραγματοποιήθηκαν αλλαγές σε βιβλιοθήκες, ρυθμίσεις και βοηθητικό κώδικα, ώστε το σύστημα να μπορεί να εκτελεστεί και σε περιβάλλον macOS για ανάγκες προσωπικής ανάπτυξης και απομακρυσμένης εργασίας. Η προσαρμογή αυτή δεν πρέπει να συγχέεται με το πειραματικό περιβάλλον, το οποίο παραμένει Windows λόγω της χρήσης του eye tracker και της διάταξης του εργαστηριακού setup. Παρ' όλα αυτά, η δυνατότητα ανάπτυξης σε macOS αύξησε την ευελιξία συντήρησης του κώδικα και επέτρεψε ταχύτερες δοκιμές χωρίς αποκλειστική εξάρτηση από τον πειραματικό υπολογιστή.

Παράλληλα, αναδιοργανώθηκε η διαχείριση διαπιστευτηρίων των μεταφραστικών παρόχων. Σε προηγούμενες πειραματικές εκδόσεις υπήρχαν hardcoded ή front-end exposed τιμές, κάτι που δεν είναι αποδεκτό για ασφαλή ανάπτυξη. Η τελική λογική μεταφέρθηκε στο backend, ενώ τα API keys διαβάζονται από τοπικό περιβάλλον ή μη tracked .env αρχείο. Με αυτόν τον τρόπο ο browser δεν έχει άμεση πρόσβαση στο μεταφραστικό κλειδί και ο server λειτουργεί ως ενιαίο σημείο ελέγχου για μετάφραση, logging, error handling και μελλοντική αλλαγή παρόχου.

Η συγκεκριμένη αλλαγή έχει κυρίως μη λειτουργικό αλλά ουσιαστικό χαρακτήρα: δεν αλλάζει άμεσα αυτό που βλέπει ο χρήστης, όμως αυξάνει την ασφάλεια, τη συντηρησιμότητα και την αναπαραγωγιμότητα της εφαρμογής. Σε επίπεδο διπλωματικής, πρέπει να παρουσιαστεί ως βελτίωση υποδομής και όχι ως απλή αλλαγή configuration.

4.2 Βελτιώσεις διεπαφής χρήστη και παραμετροποίησης
Η διεπαφή χρήστη επεκτάθηκε ώστε να υποστηρίζει πιο ακριβή και κατανοητή παραμετροποίηση. Ρυθμίσεις που αρχικά ήταν διαθέσιμες μόνο μέσω slider απέκτησαν και αριθμητικό πεδίο εισαγωγής. Η αλλαγή αυτή είναι σημαντική σε πειραματικό πλαίσιο, διότι επιτρέπει στον ερευνητή να επαναφέρει ακριβείς τιμές και να συγκρίνει συνεδρίες με μεγαλύτερη συνέπεια. Για παράδειγμα, η ρύθμιση του χρόνου εστίασης πριν από τη μετάφραση δεν είναι απλώς προτίμηση χρήστη, αλλά παράμετρος που επηρεάζει άμεσα τον αριθμό και το είδος των μεταφραστικών ενεργοποιήσεων.

Στο panel ρυθμίσεων προστέθηκαν επιλογές που υποστηρίζουν τόσο την κανονική χρήση όσο και τη διάγνωση προβλημάτων. Η επιλογή Show word boxes εμφανίζει τα OCR bounding boxes πάνω από το PDF, επιτρέποντας στον ερευνητή να ελέγξει αν οι λέξεις έχουν χαρτογραφηθεί σωστά στην οθόνη. Η επιλογή Hover translate debug ενεργοποιεί την ίδια ροή μετάφρασης με χρήση του κέρσορα αντί για gaze input. Η λειτουργία αυτή χρησιμοποιήθηκε κυρίως για γρήγορο έλεγχο της μεταφραστικής ροής, χωρίς να απαιτείται ενεργή σύνδεση eye tracker. Η επιλογή Show gaze cursor κάνει προαιρετική την οπτική απεικόνιση του gaze, ώστε ο χρήστης ή ο πειραματιστής να μπορεί να την ενεργοποιεί μόνο όταν είναι χρήσιμη.

Επιπλέον, προστέθηκαν ρυθμίσεις για translation mode, translation output, gaze detection mode, gaze mapping mode, gaze hit radius και X/Y offsets. Οι ρυθμίσεις αυτές μετατρέπουν το σύστημα από στατικό prototype σε παραμετροποιήσιμο εργαλείο. Η ανάγκη για παραμετροποίηση προκύπτει από τη φύση του eye tracking: διαφορετικοί χρήστες, διαφορετική στάση σώματος, διαφορετική βαθμονόμηση και διαφορετικά setups οθόνης παράγουν διαφορετικά επίπεδα απόκλισης.

4.3 Αναδιοργάνωση OCR pipeline και διαχωρισμός data/tokensAll
Το backend OCR pipeline τροποποιήθηκε ώστε να επιστρέφει δύο διακριτές λίστες για κάθε σελίδα. Η πρώτη λίστα, data, περιέχει τις φιλτραρισμένες λέξεις που είναι κατάλληλες για gaze trigger. Από αυτήν αφαιρούνται tokens χαμηλής εμπιστοσύνης, σημεία στίξης, πολύ μικρές λέξεις, stopwords, URLs, emails και άλλα στοιχεία που δεν είναι κατάλληλα για ενεργοποίηση μετάφρασης. Η δεύτερη λίστα, tokensAll, διατηρεί τα raw OCR tokens, συμπεριλαμβανομένων των σημείων στίξης και των μεταδεδομένων θέσης, γραμμής, παραγράφου και block.

Ο διαχωρισμός αυτός λύνει ένα βασικό πρόβλημα. Για την ανίχνευση βλέμματος χρειάζεται μια καθαρή λίστα υποψήφιων λέξεων, ώστε να μειώνονται τα άχρηστα triggers. Για την ανακατασκευή πρότασης, όμως, χρειάζεται η πλήρης OCR πληροφορία. Αν η στίξη και οι μικρές λέξεις αφαιρεθούν εντελώς, το σύστημα δεν μπορεί να εντοπίσει αξιόπιστα τα όρια πρότασης. Επομένως, το σύστημα χρησιμοποιεί διαφορετική αναπαράσταση δεδομένων για διαφορετικό σκοπό: filtered words για hit-testing και raw tokens για context extraction.

Στο ίδιο στάδιο προστέθηκε και κανονικοποίηση συγκεκριμένων OCR σφαλμάτων, όπως η σύγχυση του κεφαλαίου I με κάθετη μπάρα. Η κανονικοποίηση αυτή εφαρμόζεται πριν από τη μετάφραση και κατά την ανακατασκευή της πρότασης, ώστε να μειώνονται συστηματικά σφάλματα εισόδου που μπορούν να επηρεάσουν τόσο την ποιότητα μετάφρασης όσο και την επιλογή της σωστής λέξης.

4.4 Διόρθωση word boxes και κοινή γεωμετρική χαρτογράφηση
Μία από τις πιο σημαντικές τεχνικές αλλαγές ήταν η διόρθωση της γεωμετρικής αντιστοίχισης των word boxes. Το OCR παράγει boxes σε σύστημα συντεταγμένων της εικόνας που επεξεργάστηκε το Tesseract. Ο χρήστης, όμως, βλέπει το PDF ως rendered canvas μέσα στο browser, με zoom, scrolling, browser scaling και CSS layout. Αν αυτά τα δύο συστήματα συντεταγμένων δεν αντιστοιχιστούν σωστά, το σύστημα μπορεί να θεωρήσει ότι το βλέμμα βρίσκεται πάνω σε διαφορετική λέξη από αυτή που βλέπει ο χρήστης.

Για να διορθωθεί το πρόβλημα, το backend επιστρέφει πλέον μαζί με κάθε σελίδα και τις πραγματικές διαστάσεις της εικόνας OCR. Το front-end χρησιμοποιεί αυτές τις διαστάσεις και το πραγματικό DOM canvas της τρέχουσας σελίδας για να υπολογίσει ξεχωριστή κλίμακα στον άξονα X και στον άξονα Y. Η συνάρτηση calculateScaledPositions παίρνει το raw OCR box, βρίσκει το canvas μέσω data-page-number και διαβάζει τη rendered θέση και διάσταση με getBoundingClientRect. Με βάση αυτά παράγει τις τελικές συντεταγμένες οθόνης.

Η χρήση getBoundingClientRect είναι ιδιαίτερα σημαντική, διότι λαμβάνει υπόψη το τελικό rendered αποτέλεσμα. Έτσι η χαρτογράφηση δεν εξαρτάται μόνο από το zoom της εφαρμογής, αλλά επηρεάζεται σωστά και από το browser page zoom, το layout και το scrolling. Με άλλα λόγια, το σύστημα δεν υπολογίζει πού θα έπρεπε θεωρητικά να βρίσκεται η λέξη, αλλά πού βρίσκεται πράγματι στο viewport τη στιγμή της ανίχνευσης.

Η ίδια συνάρτηση χρησιμοποιείται από το TextBox, που εκτελεί το hit-testing, και από το WordBoxesOverlay, που εμφανίζει τα debug boxes. Με αυτόν τον τρόπο το overlay δεν είναι απλώς οπτική ένδειξη, αλλά απεικόνιση της πραγματικής γεωμετρίας που χρησιμοποιείται από την εφαρμογή. Αυτό είναι κρίσιμο για debugging, επειδή ο ερευνητής μπορεί να ελέγξει οπτικά αν η εφαρμογή μεταφράζει με βάση τα σωστά boxes.

4.5 Recalculation των boxes σε zoom και scrolling
Η θέση μιας λέξης στο viewport δεν είναι σταθερή. Μεταβάλλεται όταν ο χρήστης αλλάζει zoom, όταν μετακινείται κάθετα στη σελίδα και όταν μετακινείται οριζόντια. Η οριζόντια μετακίνηση είναι ιδιαίτερα σημαντική σε υψηλά zoom levels, όπου το PDF δεν χωράει ολόκληρο στο πλάτος του viewer. Για αυτό το σύστημα επεκτάθηκε ώστε να παρακολουθεί τόσο scrollTop όσο και scrollLeft.

Όταν αλλάζει το scrollTop ή το scrollLeft, το TextBox και το WordBoxesOverlay επανυπολογίζουν τις θέσεις των λέξεων με βάση το νέο getBoundingClientRect του canvas. Αν ο χρήστης κάνει zoom στο PDF, το react-pdf rerenderάρει τη σελίδα με νέο scale και η επόμενη χαρτογράφηση χρησιμοποιεί τις νέες διαστάσεις. Αν αλλάξει το browser zoom, το DOM rect αλλάζει επίσης και η κλίμακα προσαρμόζεται έμμεσα. Με αυτόν τον τρόπο η εφαρμογή διατηρεί συγχρονισμένη τη θέση των boxes, του overlay, του gaze cursor και του translation popup.

Η συγκεκριμένη λειτουργία είναι απαραίτητη για την εγκυρότητα του πειράματος. Αν τα boxes δεν επανυπολογίζονταν, μια μετάφραση θα μπορούσε να ενεργοποιηθεί σε λάθος λέξη μόνο και μόνο επειδή ο χρήστης μετακίνησε τη σελίδα. Αυτό θα δημιουργούσε θόρυβο στα αποτελέσματα και θα μείωνε την εμπιστοσύνη στο σύστημα.

4.6 Κοινή ροή eye tracker και hover debug
Μετά τις αλλαγές, το σύστημα ακολουθεί κοινή λογική ανεξάρτητα από το αν η λέξη ενεργοποιείται από eye tracker ή από hover debug. Το WordPositionsProvider φορτώνει τις θέσεις λέξεων από το backend. Το TextBox μετατρέπει τις OCR θέσεις σε οθονικές θέσεις και δημιουργεί τον πίνακα wordsScreenPositions. Αυτός ο πίνακας χρησιμοποιείται είτε από τη gaze ανίχνευση είτε από τον κέρσορα.

Όταν το hover debug είναι απενεργοποιημένο, το σύστημα ελέγχει τα gaze samples σε σχέση με τα wordsScreenPositions. Όταν το hover debug είναι ενεργό, ένας mousemove listener ελέγχει αν ο κέρσορας βρίσκεται μέσα σε κάποιο από τα ίδια boxes. Σε περίπτωση επιτυχίας, ορίζεται το ίδιο currentWord και ενεργοποιείται η ίδια ροή μετάφρασης. Άρα το hover debug δεν είναι δεύτερη υλοποίηση, αλλά ελεγχόμενο trigger της ίδιας λειτουργίας.

Η λειτουργία αυτή ήταν χρήσιμη κυρίως κατά την ανάπτυξη, επειδή επέτρεψε έλεγχο της μετάφρασης, του sentence extraction και του popup χωρίς τη μεταβλητότητα του eye tracker. Στο τελικό πείραμα, όμως, η κύρια είσοδος παραμένει το gaze.

4.7 Παραμετροποίηση gaze mapping και detection
Το gaze mapping επεκτάθηκε ώστε να αντιμετωπίζει τις πρακτικές αποκλίσεις μεταξύ eye tracker, οθόνης και browser. Το Tobii επιστρέφει normalized συντεταγμένες, αλλά η εφαρμογή χρειάζεται viewport/client συντεταγμένες. Σε non-fullscreen παράθυρα, σε browsers με toolbars και σε extended display setups, η διαφορά αυτή μπορεί να δημιουργήσει συστηματικό offset.

Για αυτό προστέθηκαν τρία mapping modes. Το viewport mode μετατρέπει απευθείας τις normalized τιμές σε διαστάσεις viewport. Το screenAdjusted mode υπολογίζει absolute screen pixels και αφαιρεί την εκτιμώμενη θέση του browser viewport πάνω στην οθόνη. Το auto mode επιλέγει την πιο λογική λύση με βάση το πόσο εκτός viewport καταλήγει το αποτέλεσμα. Επιπλέον, τα gazeXOffsetPx και gazeYOffsetPx επιτρέπουν χειροκίνητη διόρθωση μικρών ή μεγάλων αποκλίσεων. Η δυνατότητα αρνητικού και θετικού Y offset και η εισαγωγή X offset ήταν σημαντικές για πραγματικά setups, ειδικά όταν υπήρχε δεύτερη οθόνη.

Η ανίχνευση λέξης οργανώθηκε σε δύο modes. Το Point mode διατηρεί την αυστηρή αρχική λογική και απαιτεί τα gaze samples να βρίσκονται μέσα στο box της λέξης. Το Circle mode εισάγει ακτίνα αβεβαιότητας και αξιολογεί τις υποψήφιες λέξεις με βάση hit ratio και απόσταση. Η προσθήκη Circle mode βελτιώνει την ανθεκτικότητα σε calibration noise, ενώ το Point mode παραμένει διαθέσιμο για περιπτώσεις όπου χρειάζεται αυστηρό debugging ή μέγιστη ακρίβεια.

Για λόγους απόδοσης, ο detection pipeline δεν εκτελεί βαρείς υπολογισμούς σε κάθε μικρή αλλαγή χωρίς περιορισμό. Εφαρμόζεται throttling και candidate preselection, ώστε να εξετάζονται πρώτα οι πιο πιθανές λέξεις. Αυτή η βελτίωση μειώνει το CPU load και το lag σε πιο αδύναμα PCs, χωρίς να αλλάζει η βασική λογική του συστήματος.

4.8 Εξαγωγή πρότασης από focus box
Για την υποστήριξη sentence-level και context-aware translation υλοποιήθηκε endpoint /api/sentence-from-focus. Το endpoint λαμβάνει docID, userID, page και focusBox. Το focusBox είναι το OCR box της λέξης που ενεργοποιήθηκε από gaze ή hover. Το backend αναζητά στο tokensAll το token με τη μεγαλύτερη επικάλυψη με το focusBox. Με αυτόν τον τρόπο η αντιστοίχιση γίνεται στη γλώσσα της OCR γεωμετρίας και όχι αποκλειστικά με βάση το string της λέξης.

Αφού εντοπιστεί το token, το backend περιορίζει την αναζήτηση στο ίδιο block και paragraph όταν υπάρχουν επαρκή δεδομένα. Στη συνέχεια κινείται προς τα πίσω και προς τα εμπρός μέχρι να βρει όρια πρότασης, όπως σημεία στίξης. Από τα tokens αυτά ανακατασκευάζεται η πρόταση και επιστρέφονται τόσο η πρόταση όσο και το matchedToken. Αυτό επιτρέπει στο front-end να γνωρίζει ποια ακριβώς OCR λέξη ενεργοποιήθηκε και ποιο είναι το συμφραζόμενο κείμενο στο οποίο ανήκει.

Η διαδικασία αυτή είναι σημαντική επειδή το gaze detection μπορεί να ξεκινά από screen coordinates, αλλά η μετάφραση χρειάζεται γλωσσική μονάδα. Το focusBox λειτουργεί ως γέφυρα ανάμεσα στη γεωμετρία της οθόνης και στη γλωσσική αναπαράσταση του OCR.

4.9 Εξέλιξη μεταφραστικής ροής
Η μεταφραστική ροή πέρασε από διαδοχικά στάδια. Αρχικά δοκιμάστηκε context-aware προσέγγιση με markers. Σε αυτήν, η λέξη-στόχος επισημαινόταν μέσα στην πρόταση με ειδικά σημάδια, η πρόταση μεταφραζόταν και στη συνέχεια επιχειρούνταν εξαγωγή της μετάφρασης ανάμεσα στους markers. Η προσέγγιση αυτή είχε το πλεονέκτημα ότι έδινε πλήρες συμφραζόμενο στον πάροχο, όμως παρουσίαζε σημαντική αστάθεια, επειδή οι μεταφραστικές υπηρεσίες δεν εγγυώνται διατήρηση markers.

Στη συνέχεια δοκιμάστηκε Azure Translator με source-target alignment. Σε αυτή τη ροή, το backend κρατούσε character span της λέξης μέσα στην πρόταση και ζητούσε από τον Azure Translator alignment πληροφορία. Με βάση αυτή τη πληροφορία μπορούσε να χαρτογραφήσει το source span στο target span και να επιστρέψει μόνο το αντίστοιχο μεταφρασμένο τμήμα. Η προσέγγιση ήταν πιο deterministic, αλλά πρόσθετε πολυπλοκότητα και εξαρτιόταν από την ποιότητα του alignment και του OCR.

Η τελική υλοποίηση στο branch deepltest χρησιμοποιεί DeepL. Η μετάφραση εκτελείται αποκλειστικά στο backend, ώστε το API key να μην εκτίθεται στον browser. Στο word mode, το σύστημα στέλνει ως text το matchedToken και ως context την πρόταση που εξήχθη από το OCR. Στο sentence mode, στέλνει ως text ολόκληρη την πρόταση. Η επιλογή αυτή δίνει προτεραιότητα στη φυσικότητα και στη συμφραζομενική ποιότητα της μετάφρασης, αντί για ρητό alignment.

Είναι σημαντικό να διευκρινιστεί ότι στην τελική DeepL ροή η σωστή λέξη δεν αναζητείται μέσα σε μεταφρασμένη πρόταση. Η σωστή λέξη εντοπίζεται πριν από τη μετάφραση, μέσω overlap ανάμεσα στο focusBox και τα OCR tokens. Η πρόταση χρησιμοποιείται ως context για να βοηθήσει το DeepL να επιλέξει καταλληλότερη απόδοση της λέξης.

4.10 Modes εμφάνισης μετάφρασης
Το σύστημα υποστηρίζει word και sentence translation mode. Στο word mode εμφανίζεται μετάφραση της λέξης/φράσης που εντοπίστηκε από το gaze, με χρήση της πρότασης ως συμφραζόμενου. Στο sentence mode εμφανίζεται μετάφραση ολόκληρης της πρότασης. Αυτή η διάκριση είναι σημαντική, επειδή η δυσκολία του χρήστη μπορεί να αφορά είτε λεξιλογική άγνοια είτε σύνθετη συντακτική/νοηματική δομή.

Επιπλέον, προστέθηκε translation output mode. Όταν το output είναι on, η μετάφραση εμφανίζεται στο popup. Όταν είναι off, το σύστημα συνεχίζει να καταγράφει μεταφραστικά events αλλά δεν εμφανίζει μετάφραση στον χρήστη. Αυτό μπορεί να χρησιμοποιηθεί ως πειραματική συνθήκη ελέγχου ή ως τρόπος καταγραφής gaze-triggered αναγκών χωρίς άμεση παρέμβαση στην ανάγνωση.

4.11 Translation popup και undesired translation
Το translation popup τροποποιήθηκε ώστε να εμφανίζεται μόνο όταν επιστραφεί μη κενή μετάφραση. Έτσι αποφεύγεται το κενό bubble και μειώνεται το οπτικό flicker. Επιπλέον, προστέθηκε διακριτικό control για σήμανση ανεπιθύμητης μετάφρασης. Αν ο χρήστης θεωρήσει ότι η μετάφραση ενεργοποιήθηκε χωρίς πραγματική ανάγκη, μπορεί να το δηλώσει. Το event παραμένει στα Results με flag isUndesired, αλλά εξαιρείται από το Vocabulary.

Η λειτουργία αυτή είναι σημαντική για την ποιότητα των πειραματικών δεδομένων. Σε gaze-based σύστημα δεν μπορούμε να υποθέσουμε ότι κάθε ενεργοποίηση αντιστοιχεί σε πραγματική ανάγκη. Η δυνατότητα ανατροφοδότησης επιτρέπει στο σύστημα να διατηρεί το πλήρες ιστορικό, αλλά να ξεχωρίζει τα γεγονότα που δεν πρέπει να ερμηνευθούν ως χρήσιμες λεξιλογικές ανάγκες.

4.12 Session logging, Results και export
Για την πειραματική αξιοποίηση του συστήματος υλοποιήθηκε session-centric logging. Το session ξεκινά με τη σύνδεση του eye tracker και κλείνει με αποσύνδεση ή logout. Κατά τη διάρκεια του session καταγράφονται μεταφράσεις, αλλαγές ρυθμίσεων, timestamp, provider, mode, output mode, χρήστης, έγγραφο και σελίδα. Η καταγραφή αυτή επιτρέπει να συνδεθεί η συμπεριφορά του χρήστη με το πλαίσιο χρήσης και τις ρυθμίσεις που ήταν ενεργές.

Στο Results UI προστέθηκε δυνατότητα επιλογής χρήστη και session. Μετά την επιλογή session εμφανίζονται στοιχεία συνεδρίας, αρχικές ρυθμίσεις και ενιαίο χρονολογικό timeline που συνδυάζει translation events και settings changes. Η ενιαία αυτή παρουσίαση είναι σημαντική, επειδή οι αλλαγές ρυθμίσεων μπορούν να επηρεάσουν άμεσα τη συχνότητα ή την ποιότητα των μεταφράσεων. Το export επιτρέπει την εξαγωγή δεδομένων για ανάλυση σε εργαλεία όπως Excel ή Sheets.

4.13 Vocabulary ως παράγωγο του logging pipeline
Η λειτουργία Vocabulary υλοποιήθηκε ως παράγωγο των translation_events και όχι ως δεύτερη ανεξάρτητη βάση. Κάθε εγγραφή προκύπτει από καταγεγραμμένα events, με απο-διπλοποίηση ανά χρήστη, translation mode και source text. Τα undesired events και τα output-off events εξαιρούνται, ώστε το Vocabulary να αντιπροσωπεύει κυρίως χρήσιμες εμφανισμένες μεταφράσεις.

Η ίδια λογική επιτρέπει την εμφάνιση του PDF προέλευσης για κάθε εγγραφή και το φιλτράρισμα ανά έγγραφο. Έτσι ο χρήστης ή ο ερευνητής μπορεί να δει όχι μόνο ποιες λέξεις μεταφράστηκαν, αλλά και σε ποιο κείμενο εμφανίστηκαν. Η προσέγγιση αυτή διατηρεί ενιαία πηγή αλήθειας ανάμεσα στα Results και στο Vocabulary.

Σε επίπεδο πρόσβασης, οι απλοί χρήστες βλέπουν μόνο τα δικά τους δεδομένα, ενώ ο χρήστης Sotiris έχει δυνατότητα εποπτείας όλων των χρηστών για ανάγκες πειραματικής αξιολόγησης. Αυτή η λύση είναι πρακτική για το συγκεκριμένο πείραμα, αν και σε μελλοντική γενίκευση θα ήταν προτιμότερο να αντικατασταθεί από κανονικό role-based access control.

4.14 Σύνοψη τεχνικών ωφελειών και περιορισμών
Οι αλλαγές του συστήματος βελτίωσαν την ακρίβεια γεωμετρικής αντιστοίχισης, την ανθεκτικότητα του gaze detection, την ασφάλεια της μεταφραστικής ροής, τη δυνατότητα συμφραζομενικής μετάφρασης και την ποιότητα της πειραματικής καταγραφής. Η εφαρμογή μετατράπηκε από prototype βασικής λειτουργικότητας σε εργαλείο που μπορεί να υποστηρίξει επαναλαμβανόμενες πειραματικές συνεδρίες.

Παράλληλα, οι αλλαγές εισήγαγαν και νέες προκλήσεις. Η αυξημένη παραμετροποίηση απαιτεί προσεκτική καταγραφή και ερμηνεία. Η DeepL λύση δίνει καλύτερη ποιοτική μετάφραση αλλά δεν παρέχει ρητό alignment όπως το Azure branch. Το gaze mapping παραμένει εξαρτημένο από calibration και setup οθόνης. Για αυτό το σύστημα πρέπει να αντιμετωπίζεται ως ερευνητικό εργαλείο με σαφείς δυνατότητες αλλά και τεχνικά όρια.

Να αναφερθούν ως ανάπτυξη/προσωπική χρήση, όχι ως πειραματικό περιβάλλον. Θετικό: διευκόλυναν remote development. Αρνητικό: δεν επηρεάζουν άμεσα την πειραματική διαδικασία και δεν πρέπει να υπερτονιστούν.

Να αναφερθεί ως debug εργαλείο. Θετικό: ελέγχει την ίδια ροή translation χωρίς gaze noise. Αρνητικό: δεν μετρά πραγματική gaze συμπεριφορά και δεν είναι κανονική συνθήκη χρήσης.

Να παρουσιαστεί ως ενδιάμεσο πείραμα. Θετικό: προσπάθησε να δώσει context και να επιστρέψει μόνο τη λέξη. Αρνητικό: marker preservation δεν είναι εγγυημένο, parsing εύθραυστο, πιθανή αλλοίωση μετάφρασης, αρχικά front-end API exposure.

9.5 DeepL final

15. ΑΝΑΛΥΣΗ ΓΙΑ ΤΟΝ ΚΥΚΛΟ ΑΒΕΒΑΙΟΤΗΤΑΣ ΣΤΟ GAZE MAPPING ΚΑΙ ΤΙΣ ΒΕΛΤΙΩΣΕΙΣ ΑΠΟΔΟΣΗΣ

15.1 Τι υπήρχε πριν από τον κύκλο αβεβαιότητας
Στην παλιά μορφή του συστήματος, η ανίχνευση λέξης βασιζόταν σε αυστηρό point-based matching. Τα normalized Tobii gaze coordinates μετατρέπονταν σε pixels πολλαπλασιάζοντας τις τιμές με window.screen.width και window.screen.height. Στη συνέχεια το validateEyeData2 περνούσε από όλες τις λέξεις της σελίδας και για κάθε λέξη έπαιρνε τα τελευταία gaze samples. Η λέξη ενεργοποιούνταν μόνο αν όλα τα σχετικά gaze samples βρίσκονταν μέσα στο bounding box της λέξης.

Αυτή η λογική ήταν απλή, αλλά είχε τρία σοβαρά πρακτικά προβλήματα:
- Ήταν πολύ αυστηρή. Αν το βλέμμα έπεφτε λίγα pixels έξω από το κουτί, η λέξη δεν αναγνωριζόταν.
- Δεν μοντελοποιούσε την πραγματική αβεβαιότητα του eye tracker. Σε πραγματική ανάγνωση, ακόμη και μετά από calibration, το gaze έχει θόρυβο.
- Η μετατροπή screen coordinates σε browser/PDF coordinates δεν λάμβανε επαρκώς υπόψη viewport, browser chrome, scroll, δεύτερη οθόνη και rendered PDF canvas.

Στο Κεφάλαιο 3 αυτό πρέπει να παρουσιαστεί ως περιορισμός του αρχικού prototype. Το σύστημα λειτουργούσε, αλλά βασιζόταν σε ιδανική γεωμετρία και σε πολύ αυστηρή αντιστοίχιση.

15.2 Η πρώτη εισαγωγή του circle mode και γιατί προκάλεσε βάρος
Το commit c1a5599 της 2026-03-10 με μήνυμα “κυκλος αβεβαιότητας gaze αντι για px” εισήγαγε ουσιαστικά το circle/soft matching. Η αλλαγή πρόσθεσε:
- gazeHitRadiusPx στις ρυθμίσεις.
- Υπολογισμό απόστασης gaze point από το bounding box της λέξης.
- Υπολογισμό hit ratio, δηλαδή πόσα gaze points πέφτουν εντός της ακτίνας αβεβαιότητας.
- Distance-based score, ώστε να επιλεγεί η πιο πιθανή λέξη όταν περισσότερες από μία λέξεις είναι κοντά.

Η αλλαγή ήταν σωστή ως προς την ακρίβεια, γιατί το gaze δεν αντιμετωπιζόταν πλέον σαν τέλειο σημείο. Όμως στην πρώτη μορφή της είχε αυξημένο υπολογιστικό κόστος. Η συνάρτηση περνούσε από όλες τις λέξεις και, για κάθε λέξη, ξαναϋπολόγιζε/ξαναδιέτρεχε σχετικά gaze samples. Αυτό οδηγεί σε κόστος περίπου O(λέξεις * samples), με επιπλέον κόστος από μετατροπές gaze coordinates και score calculations.

Γιατί μπορούσε να “κολλάει”:
Το eye tracker μπορεί να δίνει μεγάλο αριθμό samples ανά δευτερόλεπτο. Κάθε νέο batch eyeData προκαλεί React update/effect. Αν σε κάθε τέτοιο update το σύστημα ελέγχει κάθε λέξη της σελίδας απέναντι σε δεκάδες ή εκατοντάδες gaze samples, τότε το browser thread φορτώνεται συνεχώς. Επειδή το React UI, το PDF rendering, το popup και το gaze detection τρέχουν στον browser, ο βαρύς συγχρονισμένος υπολογισμός μπορεί να κάνει την εφαρμογή να καθυστερεί, να μη δέχεται άμεσα input ή να φαίνεται ότι παγώνει.

15.3 Η βασική performance διόρθωση: throttling, κοινό mapping και candidate preselection
Το commit 42741d6 της 2026-03-10 ήταν κρίσιμο για την απόδοση. Έκανε τρεις σημαντικές αλλαγές.

Πρώτον, προστέθηκε throttling στο TextBox με lastDetectionRunAtRef και performance.now. Το detection δεν τρέχει αν έχουν περάσει λιγότερα από περίπου 45 ms από τον προηγούμενο έλεγχο. Αυτό περιορίζει την ανίχνευση σε περίπου 22 φορές ανά δευτερόλεπτο αντί να τρέχει σε κάθε μικρή αλλαγή του eyeData. Το αποτέλεσμα είναι αισθητά μικρότερο CPU load.

Δεύτερον, τα gaze points χαρτογραφούνται μία φορά για το τρέχον detection pass. Η συνάρτηση δημιουργεί έναν mapper και μετατρέπει τα relevant gaze samples σε viewport coordinates μία φορά. Πριν, υπήρχε τάση η μετατροπή να επαναλαμβάνεται μέσα στον έλεγχο κάθε λέξης. Με την αλλαγή, το κόστος mapping γίνεται O(samples), όχι O(λέξεις * samples).

Τρίτον, προστέθηκε candidate preselection. Το σύστημα υπολογίζει τον μέσο όρο των gaze points, μετρά coarse απόσταση από κάθε word box και κρατά μόνο τις 10 πιο κοντινές υποψήφιες λέξεις. Μετά κάνει τον αναλυτικό hit ratio/distance scoring μόνο σε αυτές τις 10 λέξεις. Αυτό μειώνει σημαντικά το κόστος, γιατί το ακριβό κομμάτι δεν εκτελείται για όλη τη σελίδα.

Με απλά λόγια, το σύστημα άλλαξε από “δοκίμασε όλα τα gaze samples απέναντι σε όλες τις λέξεις συνέχεια” σε “περιοδικά, βρες τις πιο πιθανές λέξεις και κάνε λεπτομερή έλεγχο μόνο εκεί”. Αυτό είναι ο κύριος λόγος που η εφαρμογή έγινε πιο λειτουργική και δεν κολλούσε τόσο.

15.4 Αφαίρεση περιττών console logs και περιορισμός state churn
Στο ίδιο στάδιο αφαιρέθηκαν console logs όπως “word detected”, “translation pops” και debug prints γύρω από coolDown/shouldTranslate. Αυτό δεν είναι απλώς αισθητική αλλαγή. Όταν ένα log τρέχει πολλές φορές ανά δευτερόλεπτο, ειδικά με αντικείμενα ή arrays, το browser DevTools και το main thread επιβαρύνονται. Σε gaze pipeline υψηλής συχνότητας, τα logs μπορούν να γίνουν πραγματικός παράγοντας καθυστέρησης.

Επίσης, η τελική λογική στο TextBox ελέγχει αν η νέα detectedWord είναι ουσιαστικά ίδια με το currentWord πριν ξανακάνει setCurrentWord και setShouldTranslate. Αυτό μειώνει περιττά React renders και αποτρέπει επαναλαμβανόμενες μεταφραστικές κλήσεις για την ίδια λέξη. Είναι σημαντικό γιατί κάθε state update μπορεί να ξανατρέξει effects, να καθαρίσει/ξαναγράψει translation state και να δημιουργήσει νέο async fetch.

15.5 Η προσωρινή releaseOutside λογική και γιατί αφαιρέθηκε
Το commit f86077c πρόσθεσε ένα επιπλέον effect που παρακολουθούσε τα τελευταία 25 gaze samples όταν υπήρχε ενεργή μετάφραση. Στόχος ήταν να κλείνει το popup όταν το βλέμμα απομακρυνόταν από την τρέχουσα λέξη, χρησιμοποιώντας releaseMargin και insideRatio.

Η ιδέα ήταν χρήσιμη για συμπεριφορά UI, αλλά πρόσθετε έναν ακόμη συνεχή υπολογισμό πάνω στο eyeData. Κάθε update έλεγχε πρόσφατα gaze samples, έκανε coordinate mapping και αποφάσιζε αν πρέπει να απενεργοποιηθεί το shouldTranslate. Το commit d4b7573 αφαίρεσε αυτή τη λογική και κράτησε πιο απλό μηχανισμό. Αυτό πιθανότατα βοήθησε στη μείωση flicker, περιττών updates και επιπλέον φόρτου.

Προτεινόμενη διατύπωση:
“Κατά την εξέλιξη του circle mode δοκιμάστηκε μηχανισμός αυτόματης απελευθέρωσης του popup όταν το βλέμμα απομακρυνόταν από τη λέξη. Η λύση αυτή δεν διατηρήθηκε, επειδή αύξανε την πολυπλοκότητα και απαιτούσε συνεχείς ελέγχους πάνω στα πρόσφατα gaze samples. Η τελική υλοποίηση προτίμησε πιο σταθερή ανίχνευση και λιγότερα state transitions.”

15.6 Διατήρηση Point mode ως legacy επιλογή
Το commit 51e621a πρόσθεσε gazeDetectionMode με επιλογές point και circle. Αυτό είναι σημαντικό γιατί το circle mode δεν αντικατέστησε απόλυτα το point mode. Το point mode έμεινε ως strict/legacy επιλογή, χρήσιμη για debugging ή για περιπτώσεις όπου η ακτίνα αβεβαιότητας προκαλεί πολλά false positives.

Η επιλογή mode είναι τεχνικά σημαντική:
- Point mode: όλα τα samples πρέπει να είναι μέσα στο box. Είναι αυστηρό, πιο απλό, αλλά μπορεί να έχει false negatives.
- Circle mode: επιτρέπει απόσταση από το box, υπολογίζει hit ratio και score. Είναι πιο ανεκτικό σε calibration noise, αλλά χρειάζεται προσεκτική ρύθμιση radius.

Στη διπλωματική πρέπει να γραφτεί ότι η αλλαγή δεν ήταν μόνο “προστέθηκε κύκλος”. Προστέθηκε παραμετροποιήσιμο μοντέλο ανίχνευσης, ώστε το σύστημα να προσαρμόζεται σε διαφορετικές συνθήκες πειράματος.

15.7 Horizontal scroll και σταθερότητα μετά από μετακίνηση στο PDF
Το commit 565f110, “horizontal scroll box recalculation”, δεν είναι άμεσα circle-performance commit, αλλά σχετίζεται με την αίσθηση ότι το σύστημα κολλάει ή συμπεριφέρεται λάθος. Πριν από αυτό, το σύστημα παρακολουθούσε κυρίως scrollTop. Σε υψηλό zoom, όμως, ο χρήστης συχνά κάνει και οριζόντιο scroll. Αν οι word screen positions δεν επανυπολογίζονται όταν αλλάζει scrollLeft, το gaze συγκρίνεται με παλιές θέσεις. Αυτό μπορεί να δώσει λάθος hits ή να μη δώσει κανένα hit, κάνοντας το σύστημα να φαίνεται ασταθές.

Με την αλλαγή:
- Το FileViewer αποθηκεύει scrollLeft από το PDF container.
- Το TextBox και το WordBoxesOverlay εξαρτώνται από scrollLeft και scrollTop.
- Όταν αλλάζει vertical ή horizontal scroll, το shouldTranslate μηδενίζεται και το coolDown καθαρίζεται.

Άρα το σύστημα μετά την αλλαγή λειτουργεί ως εξής: κάθε φορά που το PDF μετακινείται οριζόντια ή κάθετα, οι οθονικές θέσεις των OCR boxes επανυπολογίζονται με βάση το νέο DOM canvas rect. Το hit-testing γίνεται πάνω στις τρέχουσες θέσεις και όχι σε παλιά γεωμετρία.

15.8 Εμφάνιση popup μόνο μετά από πραγματική μετάφραση
Το commit 21c91c9, “bubble shows only after translation return”, άλλαξε το rendering condition του TranslationPopup ώστε να εμφανίζεται μόνο όταν υπάρχει non-empty translation. Αυτό βελτιώνει την εμπειρία χρήστη και μειώνει την αίσθηση flicker/κολλήματος. Πριν, το popup μπορούσε να εμφανιστεί αμέσως μόλις ενεργοποιούνταν shouldTranslate, ενώ η μετάφραση ακόμη δεν είχε επιστρέψει. Έτσι ο χρήστης έβλεπε άδειο ή ημιτελές bubble.

Μετά την αλλαγή, η οπτική έξοδος εμφανίζεται μόνο όταν η async μετάφραση ολοκληρωθεί και το translation.trim().length είναι μεγαλύτερο από μηδέν. Αυτό κάνει το UI πιο σταθερό.

15.9 Μεταγενέστερες βελτιώσεις mapping για extended display
Τα commits 068ae92 και 58201dc του Μαΐου 2026 βελτίωσαν την πρακτική λειτουργία του gaze mapping σε setups με δεύτερη οθόνη ή browser που δεν καλύπτει όλη την οθόνη.

Το 068ae92 πρόσθεσε:
- gazeMappingMode με auto, viewport και screenAdjusted.
- gazeXOffsetPx, με εύρος περίπου -1200 έως 1200 px.
- Λογική auto επιλογής με βάση το ποια χαρτογράφηση παράγει μικρότερο overflow εκτός viewport.

Το 58201dc επέτρεψε αρνητικό gazeYOffsetPx, δηλαδή Y offset από -200 έως 200 px, αντί μόνο θετικές τιμές. Αυτό είναι σημαντικό όταν το gaze εμφανίζεται συστηματικά πιο πάνω ή πιο κάτω από το πραγματικό σημείο.

Μετά από αυτές τις αλλαγές, το gaze pipeline λειτουργεί ως εξής:
1. Παίρνει normalized Tobii point από αριστερό/δεξί μάτι ή μέσο όρο των δύο.
2. Δημιουργεί δύο πιθανές χαρτογραφήσεις: viewportRaw και screenAdjustedRaw.
3. Αν ο χρήστης έχει επιλέξει συγκεκριμένο mode, χρησιμοποιείται αυτό.
4. Αν είναι auto, επιλέγεται η χαρτογράφηση που πέφτει πιο φυσικά μέσα στο viewport.
5. Εφαρμόζονται X/Y offsets.
6. Το αποτέλεσμα clampάρεται στο viewport.

Αυτό δεν είναι κυρίως performance optimization, αλλά reliability optimization. Μειώνει τις περιπτώσεις όπου το σύστημα φαίνεται να μην αντιδρά επειδή το gaze έχει μετατοπιστεί συστηματικά εκτός των word boxes.

15.10 Ρυθμίσεις που κάνουν το σύστημα ελέγξιμο
Το commit a31aae1 πρόσθεσε backend persistence και schema migration για τις ρυθμίσεις gazeDetectionMode, gazeMappingMode, gazeYOffsetPx, gazeXOffsetPx και gazeHitRadiusPx. Έτσι οι ρυθμίσεις δεν είναι προσωρινό front-end state αλλά αποθηκεύονται ανά userID. Αυτό είναι σημαντικό για πειραματική διαδικασία, επειδή η ερμηνεία των αποτελεσμάτων απαιτεί να ξέρουμε με ποιες παραμέτρους έτρεξε κάθε session.

Οι σημαντικές παράμετροι είναι:
- baseGazeSamples: πόσα gaze samples απαιτούνται πριν ενεργοποιηθεί μετάφραση.
- gazeDetectionMode: point ή circle.
- gazeHitRadiusPx: ακτίνα αβεβαιότητας στο circle mode.
- gazeMappingMode: auto, viewport ή screenAdjusted.
- gazeYOffsetPx και gazeXOffsetPx: χειροκίνητη διόρθωση συστηματικού offset.

15.11 Γιατί το σύστημα έγινε πιο γρήγορο και δεν “κολλάει”
Η βελτίωση δεν οφείλεται σε μία μόνο αλλαγή. Είναι συνδυασμός:
- Throttling κάθε περίπου 45 ms, ώστε το detection να μη τρέχει σε κάθε eyeData update.
- Μία χαρτογράφηση gaze samples ανά detection pass, όχι επανάληψη για κάθε λέξη.
- Candidate preselection στις 10 πιο κοντινές λέξεις.
- Αφαίρεση συνεχών console logs.
- Αποφυγή επαναλαμβανόμενου setCurrentWord όταν η ίδια λέξη παραμένει ενεργή.
- Αφαίρεση πρόσθετης releaseOutside λογικής που έκανε επιπλέον ελέγχους.
- Επανυπολογισμός boxes σε scrollLeft/scrollTop, ώστε το σύστημα να μη δουλεύει με stale συντεταγμένες.
- Εμφάνιση popup μόνο μετά την επιστροφή μετάφρασης.

Τεχνικά, το σημαντικότερο είναι ότι η τελική circle λογική μειώνει το ακριβό κομμάτι του αλγορίθμου. Αν μια σελίδα έχει W λέξεις και το σύστημα εξετάζει S gaze points, η αρχική αφελής λογική πλησίαζε W*S ελέγχους απόστασης/αντιστοίχισης. Η τελική λογική κάνει πρώτα mapping των S points, βρίσκει coarse distance για W λέξεις, κρατά 10 candidates και κάνει αναλυτικό scoring μόνο σε 10*S. Αυτό είναι πολύ πιο ελαφρύ στην πράξη.

15.12 Πλεονεκτήματα του circle mode
- Καλύτερη ανθεκτικότητα σε θόρυβο calibration.
- Λιγότερα false negatives όταν το βλέμμα είναι κοντά στη λέξη αλλά όχι ακριβώς μέσα στο box.
- Πιο φυσική μοντελοποίηση του eye tracker, επειδή το gaze αντιμετωπίζεται ως περιοχή αβεβαιότητας και όχι ως τέλειο pixel.
- Δυνατότητα προσαρμογής ακτίνας ανά συμμετέχοντα/συνθήκη.
- Καλύτερη εμπειρία χρήστη σε πραγματική ανάγνωση, όπου το μάτι δεν μένει σταθερό πάνω σε ένα ιδανικό σημείο.

15.13 Μειονεκτήματα και περιορισμοί του circle mode
- Αν το gazeHitRadiusPx είναι πολύ μεγάλο, αυξάνονται τα false positives, ειδικά σε πυκνό κείμενο.
- Το candidate preselection βασίζεται στον μέσο όρο των gaze points. Αν τα samples έχουν μεγάλη διασπορά ή ο χρήστης μετακινεί γρήγορα το βλέμμα, υπάρχει περίπτωση να επιλεγούν λάθος candidates.
- Το throttling μειώνει το CPU load, αλλά προσθέτει μικρή χρονική καθυστέρηση έως περίπου 45 ms.
- Η σωστή λειτουργία εξαρτάται ακόμη από calibration και από το αν οι scaled OCR boxes είναι σωστά.
- Η τελική λύση δεν χρησιμοποιεί spatial index, π.χ. grid/R-tree. Για πολύ μεγάλες σελίδες με πολλά tokens, θα μπορούσε να βελτιωθεί περαιτέρω.
- Το circle mode χρειάζεται documentation/πρωτόκολλο ρύθμισης, επειδή διαφορετικές τιμές radius/baseGazeSamples αλλάζουν τη συμπεριφορά του πειράματος.

15.14 Προτεινόμενο κείμενο για τη διπλωματική
“Κατά την αρχική εισαγωγή της ανίχνευσης με κύκλο αβεβαιότητας, το σύστημα παρουσίασε σημαντική επιβάρυνση, επειδή η εφαρμογή έπρεπε να συγκρίνει συνεχώς πολλά gaze samples με πολλά word boxes. Η τελική υλοποίηση βελτιώθηκε με περιορισμό του ρυθμού εκτέλεσης του αλγορίθμου, με προϋπολογισμό των gaze coordinates, με επιλογή λίγων υποψήφιων λέξεων βάσει απόστασης και με αποφυγή περιττών React state updates. Έτσι διατηρήθηκε το πλεονέκτημα του circle mode, δηλαδή η ανθεκτικότητα στην αβεβαιότητα του eye tracker, χωρίς να επιβαρύνεται υπερβολικά το UI thread.”

16. ΛΕΠΤΟΜΕΡΗΣ ΕΞΗΓΗΣΗ ΤΩΝ .ENV ΑΡΧΕΙΩΝ ΚΑΙ ΓΙΑΤΙ ΕΙΝΑΙ ΣΗΜΑΝΤΙΚΑ

16.1 Ποια .env αρχεία υπάρχουν
Στην τρέχουσα κατάσταση υπάρχουν δύο local .env αρχεία:
- back-end/.env
- front-end/.env

Και τα δύο αγνοούνται από το git μέσω .gitignore, άρα δεν πρέπει να γίνονται commit. Το back-end/.env περιέχει πραγματικά credentials για DeepL και Azure. Το front-end/.env περιέχει REACT_APP_SHOW_BOXES, αλλά στην τρέχουσα υλοποίηση το show boxes ελέγχεται από userSettingsUi.showBoxes και το Settings UI, όχι από process.env.REACT_APP_SHOW_BOXES. Επομένως το front-end/.env φαίνεται να είναι παλαιότερο ή ανενεργό configuration.

16.2 Πώς φορτώνεται το back-end/.env
Το backend δεν χρησιμοποιεί python-dotenv. Υπάρχει χειροκίνητη υλοποίηση στο back-end/config.py.

Η ροή είναι:
1. Το app.py κάνει import τη load_config από config.py.
2. Η load_config καλεί πρώτα load_env_file.
3. Η load_env_file βρίσκει το αρχείο back-end/.env με βάση το Path(__file__).resolve().parent, δηλαδή τον φάκελο όπου βρίσκεται το config.py. Αυτό σημαίνει ότι η φόρτωση δεν εξαρτάται από το current working directory.
4. Διαβάζει το .env γραμμή-γραμμή.
5. Αγνοεί κενές γραμμές και γραμμές που αρχίζουν με #.
6. Αν μια γραμμή αρχίζει με export, αφαιρεί το export.
7. Χωρίζει τη γραμμή στο πρώτο =.
8. Κάνει trim σε key και value.
9. Αν η τιμή είναι μέσα σε μονά ή διπλά εισαγωγικά, αφαιρεί τα εξωτερικά quotes.
10. Αν το key δεν υπάρχει ήδη στο os.environ, το προσθέτει.
11. Μετά η load_config διαβάζει το back-end/appsettings.json και επιστρέφει το JSON configuration.

Το σημείο 10 είναι πολύ σημαντικό. Το .env δεν αντικαθιστά μεταβλητές που έχουν ήδη οριστεί στο process environment. Άρα αν ο server ξεκινήσει με DEEPL_API_KEY ήδη ορισμένο από shell, Docker, CI ή deployment environment, αυτή η τιμή έχει προτεραιότητα απέναντι στο .env.

16.3 Πώς χρησιμοποιεί το app.py τις DeepL μεταβλητές
Στην αρχή του app.py φορτώνονται οι ρυθμίσεις:
- config_data = load_config()
- listening_port από config_data['ETSUIConfig']['ListeningPort']
- ETSDVM_address από config_data['ETSUIConfig']['ETSDVMport']
- deepl_config από config_data.get('DeepLTranslator', {})

Μετά οι DeepL τιμές ορίζονται με os.getenv και fallback στο appsettings.json:
- DEEPL_API_KEY: από environment ή DeepLTranslator.ApiKey.
- DEEPL_TRANSLATOR_ENDPOINT: από environment ή DeepLTranslator.Endpoint, default https://api-free.deepl.com/v2/translate.
- DEEPL_MODEL_TYPE: από environment ή DeepLTranslator.ModelType, default quality_optimized.
- DEEPL_SPLIT_SENTENCES: από environment ή DeepLTranslator.SplitSentences, default 0.
- DEEPL_TRANSLATOR_TIMEOUT_SECONDS: από environment ή DeepLTranslator.TimeoutSeconds, με fallback 12 αν η τιμή δεν είναι integer.

Επειδή το load_env_file έχει ήδη φορτώσει το back-end/.env στο os.environ, το app.py βλέπει τις τιμές σαν κανονικές environment variables.

16.4 Τι συμβαίνει στο /api/translate
Το endpoint /api/translate λειτουργεί ως server-side proxy/adapter προς DeepL.

Η ροή είναι:
1. Το frontend στέλνει JSON με text, context, src/tgt και mode.
2. Το backend καθαρίζει/κανονικοποιεί το text και το context.
3. Το target language περνά από _normalize_deepl_language. Για παράδειγμα, GR μετατρέπεται σε EL, επειδή το DeepL περιμένει EL για ελληνικά.
4. Αν δεν υπάρχει text, επιστρέφεται 400.
5. Αν δεν υπάρχει DEEPL_API_KEY, επιστρέφεται 500 με μήνυμα ότι το DeepL API key δεν έχει ρυθμιστεί στον server.
6. Δημιουργείται payload με text ως λίστα, target_lang, source_lang, preserve_formatting, model_type και split_sentences.
7. Αν υπάρχει context, προστίθεται στο payload.
8. Το backend κάνει POST στο DEEPL_TRANSLATOR_ENDPOINT.
9. Το Authorization header έχει μορφή DeepL-Auth-Key <key>.
10. Αν το DeepL επιστρέψει σφάλμα, το backend επιστρέφει 502.
11. Αν υπάρχει μετάφραση, το backend επιστρέφει translation, provider=deepl, mode, sourceText, contextUsed, modelTypeRequested και modelTypeUsed.

Σημαντικό:
Το API key δεν στέλνεται ποτέ στον browser. Ο browser βλέπει μόνο το backend endpoint. Αυτό είναι βασικός λόγος ύπαρξης του .env.

16.5 Γιατί είναι σημαντικό να υπάρχει .env
Το .env είναι σημαντικό για τέσσερις λόγους.

Πρώτον, ασφάλεια. Τα credentials δεν πρέπει να βρίσκονται σε source code ή σε frontend bundle. Αν ένα API key μπει στο React frontend, μπορεί να καταλήξει στο JavaScript bundle και να είναι ορατό στον χρήστη ή σε οποιονδήποτε ανοίξει τα developer tools. Με το backend .env, το key μένει server-side.

Δεύτερον, αναπαραγωγιμότητα. Το ίδιο codebase μπορεί να τρέξει σε διαφορετικά μηχανήματα με διαφορετικά credentials ή endpoints χωρίς αλλαγή κώδικα. Ο κώδικας παραμένει ίδιος, αλλά το περιβάλλον αλλάζει.

Τρίτον, ευελιξία παρόχου/παραμέτρων. Μπορεί να αλλάξει endpoint, timeout, model_type ή split_sentences χωρίς code change. Αυτό είναι χρήσιμο όταν συγκρίνεται latency, ποιότητα ή provider behavior.

Τέταρτον, καθαρός διαχωρισμός config και logic. Το app.py υλοποιεί τη λογική μετάφρασης, ενώ το .env/appsettings.json δηλώνουν παραμέτρους εκτέλεσης. Αυτό κάνει το σύστημα πιο συντηρήσιμο.

16.6 Σχέση .env και appsettings.json
Το appsettings.json λειτουργεί ως fallback/default configuration. Περιέχει ETSUIConfig και translator sections, αλλά τα API keys εκεί είναι κενά. Αυτό είναι σωστό από άποψη ασφάλειας, επειδή το αρχείο μπορεί να είναι tracked χωρίς να περιέχει μυστικά.

Το .env λειτουργεί ως local secret configuration. Στην πράξη:
- Αν DEEPL_API_KEY υπάρχει στο process environment ή στο .env, η μετάφραση δουλεύει.
- Αν δεν υπάρχει, το /api/translate αποτυγχάνει με server-side configuration error.
- Αν το endpoint ή timeout λείπει, χρησιμοποιούνται defaults από appsettings.json.

Προτεινόμενη διατύπωση:
“Το appsettings.json περιγράφει μη μυστικές προεπιλεγμένες παραμέτρους, ενώ το .env περιέχει τοπικές ή deployment-specific τιμές, όπως API keys. Με αυτόν τον διαχωρισμό, ο κώδικας μπορεί να παραμένει στο repository χωρίς να εκτίθενται credentials.”

16.7 Azure μεταβλητές στο .env
Το back-end/.env περιέχει και Azure translator μεταβλητές. Στην τελική γραμμή deepltest, το app.py χρησιμοποιεί DeepL για /api/translate. Οι Azure μεταβλητές πρέπει να παρουσιαστούν ως κατάλοιπο/υποστήριξη σύγκρισης με το test2 branch, όχι ως ενεργή τελική ροή του deepltest.

Στη διπλωματική πρέπει να αποφευχθεί η εντύπωση ότι το τελικό σύστημα χρησιμοποιεί ταυτόχρονα Azure και DeepL. Η σωστή διατύπωση είναι ότι το Azure αποτέλεσε πειραματική διαδρομή στο branch test2, ενώ η τελική ενεργή μετάφραση στο deepltest είναι DeepL.

16.8 Τι λείπει: .env.example
Δεν υπάρχει tracked .env.example. Αυτό είναι πρόβλημα αναπαραγωγιμότητας/documentation. Το repository αγνοεί σωστά τα πραγματικά .env, αλλά θα ήταν χρήσιμο να υπάρχει ένα μη μυστικό αρχείο παράδειγμα, π.χ.:

DEEPL_API_KEY=your_deepl_key_here
DEEPL_TRANSLATOR_ENDPOINT=https://api-free.deepl.com/v2/translate
DEEPL_TRANSLATOR_TIMEOUT_SECONDS=12
DEEPL_MODEL_TYPE=quality_optimized
DEEPL_SPLIT_SENTENCES=0

Το .env.example δεν πρέπει να περιέχει πραγματικές τιμές. Πρέπει να δείχνει μόνο ποια keys απαιτούνται.

16.9 Κίνδυνοι αν δεν υπάρχει σωστό .env
Αν το .env λείπει ή είναι λάθος:
- Το backend μπορεί να ξεκινήσει, αλλά η μετάφραση DeepL θα αποτύχει όταν κληθεί /api/translate.
- Τα πειραματικά sessions μπορεί να καταγράψουν λιγότερα ή καθόλου translation events, επειδή δεν θα υπάρχει translatedText.
- Ο χρήστης μπορεί να βλέπει ότι το gaze trigger δουλεύει αλλά δεν εμφανίζεται μετάφραση.
- Αν κάποιος βάλει key στο frontend αντί στο backend, αυξάνεται σοβαρά ο κίνδυνος έκθεσης credentials.

16.10 Προτεινόμενο κείμενο για Κεφάλαιο 4 σχετικά με .env
“Η τελική υλοποίηση χρησιμοποιεί αρχείο .env στο backend για τη διαχείριση των διαπιστευτηρίων του μεταφραστικού παρόχου. Το αρχείο αυτό φορτώνεται κατά την εκκίνηση του Flask server και οι τιμές του διαβάζονται ως environment variables. Η μεταφραστική κλήση προς DeepL εκτελείται αποκλειστικά από το backend, με αποτέλεσμα το API key να μην εκτίθεται στον browser. Το appsettings.json διατηρεί μη μυστικές προεπιλογές, ενώ το .env περιέχει τις τοπικές μυστικές τιμές. Με αυτόν τον τρόπο επιτυγχάνεται διαχωρισμός κώδικα και configuration, ασφαλέστερη διαχείριση credentials και δυνατότητα εκτέλεσης του ίδιου κώδικα σε διαφορετικά περιβάλλοντα.”

17. ΕΜΠΛΟΥΤΙΣΜΟΣ ΚΕΦΑΛΑΙΟΥ 3: ΠΩΣ ΛΕΙΤΟΥΡΓΟΥΣΕ ΤΟ ΣΥΣΤΗΜΑ ΠΡΙΝ ΑΠΟ ΤΗΝ ΠΑΡΟΥΣΑ ΕΠΕΚΤΑΣΗ

17.1 Συνολική εικόνα του παλαιού ETS
Το παλαιό ETS, όπως φαίνεται στο origin/master, ήταν λειτουργικό prototype. Περιλάμβανε:
- Βασικό authentication.
- Επιλογή και φόρτωση PDF.
- Σύνδεση με eye tracker μέσω ETSDVM/websocket.
- OCR preprocessing για εξαγωγή word boxes.
- React PDF viewer.
- Gaze-based επιλογή λέξης.
- Translation popup.
- Βασικά settings όπως language, theme και zoom.

Η σημαντική επιστημονική διατύπωση είναι ότι το παλαιό σύστημα απέδειξε εφικτότητα, αλλά δεν ήταν ακόμη ώριμο πειραματικό εργαλείο. Η παρούσα εργασία δεν αντικαθιστά απλώς UI στοιχεία. Σταθεροποιεί γεωμετρία, translation pipeline, gaze tolerance, settings persistence και logging.

17.2 Παλαιό OCR pipeline
Στο παλιό backend, το process_single_page μετέτρεπε PDF page σε εικόνα και, όταν υπήρχε zoom/scaling, εφάρμοζε διαφορετικούς εμπειρικούς πολλαπλασιαστές για πλάτος και ύψος. Το process_page επέστρεφε μόνο filtered words, δηλαδή λέξεις καθαρισμένες από σημεία στίξης, αριθμούς, stopwords, URLs και emails.

Περιορισμός:
Η έξοδος δεν περιείχε width/height της OCR εικόνας ούτε tokensAll. Χωρίς width/height, το frontend έπρεπε να κάνει υποθέσεις για τη μετατροπή OCR coordinates σε DOM coordinates. Χωρίς tokensAll, το σύστημα δεν μπορούσε να ανακατασκευάσει αξιόπιστα την πρόταση γύρω από τη λέξη, επειδή είχαν αφαιρεθεί raw tokens και punctuation.

Τελική αλλαγή:
Η τρέχουσα μορφή επιστρέφει για κάθε σελίδα width, height, data και tokensAll. Το data χρησιμοποιείται για gaze trigger, ενώ το tokensAll χρησιμοποιείται για sentence reconstruction και matchedToken.

17.3 Παλαιό frontend scaling των boxes
Στο παλιό front-end, η calculateScaledPositions βασιζόταν σε στοιχεία όπως pdf-container, pdf-page, header και footer. Υπολόγιζε horizontalMargin, αφαιρούσε scrollTop και πρόσθετε μικρά hardcoded offsets, π.χ. -5 ή +10. Αυτό σήμαινε ότι η θέση του word box ήταν αποτέλεσμα εμπειρικής προσαρμογής και όχι ακριβής μετασχηματισμός από OCR image space σε rendered canvas space.

Περιορισμός:
Αν άλλαζε browser zoom, rendered canvas size, horizontal scroll ή layout, οι υπολογισμοί μπορούσαν να γίνουν λάθος. Επίσης, το σύστημα δεν γνώριζε πραγματικές OCR image dimensions, άρα δεν μπορούσε να υπολογίσει scaleX/scaleY με πλήρη ακρίβεια.

Τελική αλλαγή:
Η νέα calculateScaledPositions βρίσκει το wrapper με data-page-number, εντοπίζει το canvas, παίρνει getBoundingClientRect και χρησιμοποιεί OCR width/height. Έτσι η μετατροπή γίνεται με βάση την πραγματική rendered γεωμετρία.

17.4 Παλαιό gaze detection
Στο παλιό eyeTracking.ts, το getGazePointCoordinates μετέτρεπε normalized gaze points σε screen pixels με window.screen.width και window.screen.height. Το validateEyeData2 είχε baseGazePoints 60 και πρόσθετε 10 samples ανά επιπλέον γράμμα της λέξης. Για κάθε λέξη έλεγχε αν όλα τα relevant samples ήταν μέσα στο box.

Περιορισμός:
Αυτό ήταν αυστηρό και computationally ακριβό όταν επαναλαμβανόταν συχνά. Δεν υπήρχε circle uncertainty, δεν υπήρχε hit radius, δεν υπήρχε point/circle mode, δεν υπήρχε mapper για viewport/screenAdjusted και δεν υπήρχαν X/Y offsets.

Τελική αλλαγή:
Το gaze detection πλέον υποστηρίζει strict point mode και soft circle mode. Το circle mode χρησιμοποιεί ακτίνα, hit ratio, score, candidate preselection και throttling. Το mapping υποστηρίζει auto/viewport/screenAdjusted και offsets.

17.5 Παλαιά μετάφραση
Στο παλιό TextBox υπήρχε hardcoded Google API key στο frontend και η μετάφραση γινόταν με απευθείας fetch προς Google Translate URL. Παράλληλα, το παλιό backend περιείχε /api/translate με MarianMT/Helsinki-NLP model. Αυτό δείχνει ότι υπήρχαν πειραματικές ή παράλληλες μεταφραστικές διαδρομές.

Περιορισμοί:
- Η έκθεση API key στο frontend είναι κακή πρακτική ασφάλειας.
- Η απομονωμένη μετάφραση λέξης δεν χρησιμοποιεί sentence context.
- Δεν υπήρχε καθαρό server-side logging της μεταφραστικής κλήσης.
- Δεν υπήρχε σαφής provider abstraction για τη διπλωματική εξήγηση.

Τελική αλλαγή:
Η τελική ροή στέλνει τη λέξη και το context στο backend, και το backend καλεί DeepL με server-side credentials. Το frontend δεν γνωρίζει το API key.

17.6 Παλαιό popup και UI behavior
Στο παλιό TextBox, το TranslationPopup εμφανιζόταν όταν shouldTranslate ήταν true, ανεξάρτητα από το αν είχε επιστρέψει μετάφραση. Υπήρχαν επίσης πολλά console logs για detection/popup/cooldown. Το popup μπορούσε να εμφανιστεί κενό και η συχνή logging/debug συμπεριφορά μπορούσε να επιβαρύνει την αίσθηση σταθερότητας.

Τελική αλλαγή:
Το popup εμφανίζεται μόνο όταν υπάρχει μετάφραση και translationOutputMode είναι on. Υπάρχει δυνατότητα undesired feedback και logging-only output off mode.

17.7 Παλαιά settings λογική
Στο παλιό σύστημα, τα settings ήταν κυρίως language, theme και zoom. Δεν υπήρχε μόνιμη αποθήκευση των gaze-specific παραμέτρων που σήμερα είναι κρίσιμες για την πειραματική ερμηνεία.

Τελική αλλαγή:
Το backend αποθηκεύει baseGazeSamples, translationMode, translationOutputMode, gazeDetectionMode, gazeMappingMode, gazeYOffsetPx, gazeXOffsetPx και gazeHitRadiusPx. Οι αλλαγές settings καταγράφονται στο settings_change_events ώστε να μπορεί να αναλυθεί πότε και γιατί άλλαξε η συμπεριφορά του συστήματος.

17.8 Τι πρέπει να τονιστεί στο Κεφάλαιο 3
Το Κεφάλαιο 3 πρέπει να παρουσιάζει το παλιό ETS ως λειτουργικό αλλά περιορισμένο:
- Λειτουργούσε για βασικό gaze-to-word-to-translation flow.
- Δεν είχε επαρκή γεωμετρική ακρίβεια για διαφορετικά zoom/scroll/browser setups.
- Δεν είχε context-aware translation.
- Δεν είχε ασφαλή, κεντρικοποιημένη διαχείριση translation credentials.
- Δεν είχε πλούσιο session-centric logging.
- Δεν είχε ρυθμίσεις για circle/point detection, mapping modes και offsets.

Προτεινόμενο κείμενο:
“Η αρχική μορφή του ETS παρείχε το βασικό proof of concept: ο χρήστης μπορούσε να ανοίξει PDF, να συνδεθεί με eye tracker, να εντοπιστεί λέξη μέσω gaze και να εμφανιστεί μετάφραση. Ωστόσο, η χρήση του συστήματος σε πειραματικό πλαίσιο απαιτούσε μεγαλύτερη ακρίβεια και αναπαραγωγιμότητα. Για τον λόγο αυτό, η παρούσα εργασία εστίασε στη διόρθωση της γεωμετρικής αντιστοίχισης, στην παραμετροποίηση του gaze detection, στη συμφραζομενική μετάφραση, στη server-side ασφάλεια των API credentials και στη συστηματική καταγραφή των πειραματικών συμβάντων.”

18. ΕΜΠΛΟΥΤΙΣΜΟΣ ΚΕΦΑΛΑΙΟΥ 4: ΠΩΣ ΛΕΙΤΟΥΡΓΕΙ ΤΟ ΣΥΣΤΗΜΑ ΜΕΤΑ ΑΠΟ ΚΑΘΕ ΟΜΑΔΑ ΑΛΛΑΓΩΝ

18.1 Μετά τις αλλαγές υποδομής και configuration
Το σύστημα ξεκινά από το backend Flask app. Κατά την εκκίνηση, φορτώνεται το appsettings.json και το back-end/.env. Δημιουργούνται ή μεταναστεύονται οι πίνακες user_settings, user_sessions, translation_events, translation_stats, settings_change_events και vocabulary_entries. Αυτό σημαίνει ότι η εφαρμογή δεν εξαρτάται μόνο από μια χειροκίνητα έτοιμη βάση, αλλά μπορεί να προσθέσει ελλείπουσες στήλες όταν ξεκινά.

Πώς λειτουργεί μετά την αλλαγή:
- Το backend έχει defaults για όλες τις κρίσιμες ρυθμίσεις.
- Αν ένας χρήστης δεν έχει row στο user_settings, δημιουργείται με default τιμές.
- Όταν ο χρήστης αλλάζει settings, το backend αποθηκεύει και το νέο state και ένα settings_change_event.
- Τα API keys μένουν στο backend περιβάλλον.

18.2 Μετά τις αλλαγές OCR και word positions
Όταν ο χρήστης ζητήσει word positions για ένα PDF, το backend βρίσκει το docFile από τη SQLite βάση, μετατρέπει κάθε PDF page σε εικόνα και τρέχει OCR. Η έξοδος χωρίζεται σε δύο επίπεδα:
- data: καθαρή λίστα λέξεων για gaze trigger.
- tokensAll: raw OCR tokens για sentence reconstruction.

Πώς λειτουργεί μετά την αλλαγή:
- Το data αποφεύγει stopwords, URLs, emails, σημεία στίξης και πολύ μικρές λέξεις.
- Το tokensAll κρατά raw, confidence, box, line_num, par_num και block_num.
- Το page object περιέχει width και height της OCR εικόνας.
- Το backend κάνει cache/memoization ανά docID, userID και zoom/scaling factor.

Γιατί είναι σημαντικό:
Το gaze trigger χρειάζεται καθαρά targets, αλλά η context-aware μετάφραση χρειάζεται raw tokens και punctuation. Ο διαχωρισμός αυτός λύνει δύο διαφορετικές ανάγκες χωρίς να θυσιάζει τη μία για την άλλη.

18.3 Μετά τις αλλαγές box scaling
Το frontend παίρνει τα OCR boxes και τα μετατρέπει σε viewport coordinates μέσω calculateScaledPositions. Η συνάρτηση δεν βασίζεται πλέον σε εμπειρικά margins. Διαβάζει το πραγματικό DOM canvas της σελίδας και υπολογίζει scaleX/scaleY από rendered canvas size προς OCR image size.

Πώς λειτουργεί μετά την αλλαγή:
- Για κάθε λέξη παίρνει OCR box [x, y, w, h].
- Βρίσκει το canvas της σελίδας με data-page-number.
- Παίρνει left, top, width και height από getBoundingClientRect.
- Υπολογίζει xPrime, yPrime, wPrime, hPrime.
- Το ίδιο αποτέλεσμα χρησιμοποιείται από TextBox και WordBoxesOverlay.

Γιατί είναι σημαντικό:
Η οπτική απεικόνιση των boxes και η πραγματική λογική hit-testing είναι πλέον ευθυγραμμισμένες. Το debug overlay δείχνει αυτό που πραγματικά καταναλώνει ο αλγόριθμος.

18.4 Μετά τις αλλαγές scroll και zoom
Το FileViewer αποθηκεύει scrollTop και scrollLeft. Το TextBox και το WordBoxesOverlay ξαναϋπολογίζουν τις θέσεις όταν αλλάζει currentPage, pageMounted, currentPageData, scrollTop ή scrollLeft.

Πώς λειτουργεί μετά την αλλαγή:
- Σε vertical scroll αλλάζει η θέση των boxes στο viewport.
- Σε horizontal scroll αλλάζει επίσης η θέση των boxes, ειδικά σε zoom >= 1.
- Σε app zoom, το react-pdf canvas rerenderάρεται και το getBoundingClientRect δίνει νέα διαστάση.
- Σε browser zoom, το DOM rect δίνει την τελική CSS γεωμετρία που βλέπει ο χρήστης.

Γιατί είναι σημαντικό:
Το σύστημα συγκρίνει gaze με πραγματικές client coordinates. Αν οι θέσεις δεν επανυπολογιστούν, ακόμη και τέλειο gaze data θα αντιστοιχιστεί σε λάθος λέξη.

18.5 Μετά τις αλλαγές gaze mapping
Το gaze data αποθηκεύεται στο Zustand store και το TextBox το χρησιμοποιεί ως είσοδο. Κάθε Tobii sample μπορεί να έχει αριστερό μάτι, δεξί μάτι ή και τα δύο. Η τρέχουσα λογική παίρνει τον μέσο όρο όταν και τα δύο είναι valid, αλλιώς χρησιμοποιεί το valid μάτι.

Πώς λειτουργεί μετά την αλλαγή:
- Το normalized gaze point μετατρέπεται σε viewport point.
- Το mapping mode καθορίζει αν θα χρησιμοποιηθεί viewport ή screenAdjusted λογική.
- Το auto mode επιλέγει τη χαρτογράφηση με μικρότερο overflow.
- Τα X/Y offsets εφαρμόζονται μετά τη βασική χαρτογράφηση.
- Το τελικό point clampάρεται στα όρια του viewport.

Γιατί είναι σημαντικό:
Το Tobii δεν γνωρίζει από μόνο του πού βρίσκεται το PDF canvas μέσα στον browser. Η εφαρμογή πρέπει να μετατρέψει display-area coordinates σε browser client coordinates.

18.6 Μετά τις αλλαγές gaze detection
Το TextBox δεν τρέχει detection όταν υπάρχει coolDown ή όταν είναι ενεργό hoverTranslateDebug. Όταν τρέχει, ελέγχει αν υπάρχουν αρκετά eyeData samples σύμφωνα με baseGazeSamples. Μετά καλεί validateEyeData2 με mode και gazeRadiusPx.

Πώς λειτουργεί μετά την αλλαγή:
- Σε point mode, όλα τα gaze points πρέπει να πέσουν μέσα στο box.
- Σε circle mode, κάθε gaze point επιτρέπεται να βρίσκεται μέχρι gazeHitRadiusPx μακριά από το box.
- Υπολογίζεται hitRatio και score.
- Εξετάζονται μόνο οι πιο κοντινές υποψήφιες λέξεις.
- Αν βρεθεί νέα λέξη που δεν είναι ίδια με την τρέχουσα, ενημερώνεται currentWord και ενεργοποιείται shouldTranslate.

Γιατί είναι σημαντικό:
Η ανίχνευση γίνεται πιο ανεκτική στον θόρυβο χωρίς να γίνεται ανεξέλεγκτα ακριβή σε CPU.

18.7 Μετά τις αλλαγές sentence-from-focus
Όταν υπάρχει currentWord, το frontend στέλνει στο backend το sourceBox της λέξης. Το sourceBox είναι OCR-space box, όχι απλώς screen-space box. Το backend βρίσκει το raw OCR token με τη μεγαλύτερη επικάλυψη με το focusBox.

Πώς λειτουργεί μετά την αλλαγή:
- Το backend φορτώνει/caches pages_data.
- Επιλέγει τη σωστή σελίδα.
- Βρίσκει matched token μέσω overlap.
- Περιορίζει την αναζήτηση στο ίδιο block/paragraph όταν μπορεί.
- Βρίσκει sentence boundaries με punctuation.
- Επιστρέφει sentence, matchedToken και matchedTokenRaw.

Γιατί είναι σημαντικό:
Η σωστή λέξη καθορίζεται πριν τη μετάφραση. Το DeepL δεν χρησιμοποιείται για να “μαντέψει” ποια λέξη μέσα στην πρόταση κοίταξε ο χρήστης. Αυτό το κάνει το OCR/focusBox pipeline.

18.8 Μετά τις αλλαγές DeepL translation
Το frontend καλεί /api/translate. Σε word mode στέλνει text=matchedToken και context=sentence. Σε sentence mode στέλνει text=sentence και κενό context.

Πώς λειτουργεί μετά την αλλαγή:
- Το backend κανονικοποιεί γλώσσες και OCR artifacts.
- Ελέγχει ότι υπάρχει DeepL API key.
- Στέλνει POST στο DeepL endpoint.
- Αν υπάρχει context, το προσθέτει στο payload.
- Επιστρέφει τη μετάφραση και metadata provider/mode/contextUsed.

Γιατί είναι σημαντικό:
Η τελική λύση είναι context-aware χωρίς marker parsing και χωρίς έκθεση API key στο frontend.

18.9 Μετά τις αλλαγές translation output off
Όταν translationOutputMode είναι off, το σύστημα συνεχίζει να ανιχνεύει λέξεις και να καλεί τη μετάφραση, αλλά δεν εμφανίζει popup. Το event καταγράφεται με translationOutputMode=off και δεν μπαίνει στο Vocabulary.

Πώς λειτουργεί μετά την αλλαγή:
- Το effectiveTranslationMode γίνεται word όταν output mode είναι off.
- Το translatedText καταγράφεται, αλλά το setTranslation κρατά κενή οπτική έξοδο.
- Το Vocabulary φιλτράρει events με translationOutputMode off.

Γιατί είναι σημαντικό:
Επιτρέπει συνθήκη logging-only/control condition χωρίς άμεση παρέμβαση στον χρήστη.

18.10 Μετά τις αλλαγές undesired translation
Όταν ο χρήστης δει μια μετάφραση που δεν ήθελε, μπορεί να τη χαρακτηρίσει ως undesired. Το frontend καλεί /api/translation-feedback με eventID και userID.

Πώς λειτουργεί μετά την αλλαγή:
- Το translation event δεν διαγράφεται.
- Το isUndesired γίνεται 1.
- Τα Results συνεχίζουν να δείχνουν το event.
- Το Vocabulary το εξαιρεί.

Γιατί είναι σημαντικό:
Το πείραμα κρατά πλήρη καταγραφή, αλλά το λεξιλόγιο παραμένει πιο καθαρό.

18.11 Μετά τις αλλαγές Results και Vocabulary
Τα Results και Vocabulary βασίζονται στα translation_events και στα settings_change_events. Το Results δείχνει session timeline και settings snapshots. Το Vocabulary κάνει deduplication ανά translationMode και normalized sourceText και υποστηρίζει φίλτρο PDF.

Πώς λειτουργεί μετά την αλλαγή:
- Ο χρήστης Sotiris λειτουργεί ως super-viewer και μπορεί να δει όλους τους χρήστες.
- Οι υπόλοιποι χρήστες βλέπουν μόνο τα δικά τους δεδομένα.
- Το Vocabulary εμφανίζει μόνο output-on και not-undesired translations.
- Τα document names προκύπτουν από docName ή fallback από documents.

Γιατί είναι σημαντικό:
Υπάρχει single source of truth. Τα ίδια events χρησιμοποιούνται για ανάλυση και για λεξιλόγιο.

18.12 Προτεινόμενη δομή για Κεφάλαιο 4
Για μεγαλύτερη σαφήνεια, το Κεφάλαιο 4 μπορεί να οργανωθεί ως εξής:
- 4.1 Περιβάλλον εκτέλεσης, appsettings και .env.
- 4.2 Βάση δεδομένων και schema migrations.
- 4.3 OCR pipeline, data και tokensAll.
- 4.4 Μετατροπή OCR boxes σε DOM/viewport coordinates.
- 4.5 Recalculation σε zoom, vertical scroll, horizontal scroll και browser zoom.
- 4.6 Gaze mapping: viewport, screenAdjusted, auto, X/Y offsets.
- 4.7 Gaze detection: point mode, circle mode, hit radius, throttling, candidate preselection.
- 4.8 Sentence extraction από focusBox.
- 4.9 Translation evolution: marker-based, Azure alignment, τελικό DeepL context.
- 4.10 Popup behavior, output off και undesired feedback.
- 4.11 Session logging, settings changes, Results, Vocabulary και export.
- 4.12 Περιορισμοί και tradeoffs.

19. ΣΥΜΠΛΗΡΩΜΑ ΓΙΑ ΑΛΛΑ BRANCHES ΚΑΙ ΑΛΛΑΓΕΣ ΠΟΥ ΔΕΝ ΠΡΕΠΕΙ ΝΑ ΠΑΡΑΛΕΙΦΘΟΥΝ

19.1 origin/master
Το origin/master είναι το παλιό ETS reference branch. Περιέχει τις αρχικές δυνατότητες authentication, PDF loading, ETSDVM connection, OCR word positions, gaze detection και translation popup. Σταματά στο “enumerate words”. Πρέπει να χρησιμοποιηθεί στο Κεφάλαιο 3 ως βάση σύγκρισης.

19.2 origin/windows
Το origin/windows φτάνει στο commit 70c34ce “database”. Περιέχει μεταγενέστερες αλλαγές μέχρι Μάρτιο 2026, με έμφαση σε Windows setup και database κατάσταση. Δεν είναι η τελική γραμμή DeepL. Είναι χρήσιμο για να εξηγηθεί ότι το πειραματικό περιβάλλον παραμένει Windows, παρότι έγιναν macOS/development αλλαγές.

19.3 origin/win-mac-merge
Το origin/win-mac-merge είναι merge branch που συγχώνευσε mac και windows κατευθύνσεις. Περιέχει αρκετά dependency/proxy-server artifacts και δεν πρέπει να παρουσιαστεί ως καθαρή τελική υλοποίηση. Η σημασία του είναι ιστορική: δείχνει προσπάθεια ενοποίησης περιβαλλόντων.

19.4 origin/test-mac
Το origin/test-mac περιέχει την marker-based contextual translation προσέγγιση. Η λέξη-στόχος σημειωνόταν με markers μέσα στην πρόταση και το σύστημα προσπαθούσε να πάρει context-aware αποτέλεσμα. Πρέπει να παρουσιαστεί ως ενδιάμεσο πείραμα, όχι τελική λύση.

Πλεονέκτημα:
Έδινε πλήρες context στον μεταφραστικό πάροχο.

Μειονέκτημα:
Δεν υπάρχει εγγύηση ότι ο provider θα διατηρήσει τους markers. Επίσης η marker λογική είναι εύθραυστη σε αναδιατάξεις της μετάφρασης.

19.5 origin/test2
Το origin/test2 περιέχει την Azure contextual word translation με alignment. Εκεί η ιδέα ήταν να σταλεί η πρόταση και να χρησιμοποιηθεί source-target alignment για να εξαχθεί target span.

Πλεονέκτημα:
Πιο deterministic αντιστοίχιση sourceSpan-targetSpan.

Μειονέκτημα:
Περισσότερη πολυπλοκότητα, εξάρτηση από alignment πληροφορία και πιθανή ευθραυστότητα σε OCR λάθη ή συντακτικές αναδιατάξεις.

Σωστή διατύπωση:
“Το Azure branch αποτέλεσε πειραματικό στάδιο για deterministic alignment, αλλά η τελική υλοποίηση επιλέγει DeepL context με προτεραιότητα στη μεταφραστική ποιότητα και στην απλούστερη backend-controlled ροή.”

19.6 origin/mac
Το origin/mac περιέχει αλλαγές μέχρι το commit 818f81b “Normalize gitignore DB ignore entries”. Περιλαμβάνει προσπάθεια να αγνοούνται σωστά τα τοπικά SQLite αρχεία και να καθαριστεί το repository από tracked database files.

Σημαντικό:

19.7 deepltest και origin/deepltest
Το deepltest είναι η τελική λειτουργική γραμμή κώδικα με DeepL. Το origin/deepltest έχει δύο επιπλέον commits δεδομένων στη SQLite βάση, χωρίς αλλαγή κώδικα. Η διπλωματική πρέπει να περιγράφει το deepltest ως τελική υλοποίηση ως προς λειτουργικότητα, αλλά να σημειώνει ότι το remote περιέχει νεότερη βάση δεδομένων.

20. ΣΥΝΤΟΜΗ ΤΕΛΙΚΗ ΔΙΑΤΥΠΩΣΗ ΓΙΑ ΝΑ ΜΠΕΙ ΣΤΗ ΔΙΠΛΩΜΑΤΙΚΗ

“Η εξέλιξη του ETS δεν περιορίστηκε στην προσθήκη νέων οθονών ή ενός νέου μεταφραστικού παρόχου. Η κύρια τεχνική εργασία αφορούσε τη σταθεροποίηση μιας αλυσίδας πραγματικού χρόνου: OCR → word boxes → DOM scaling → gaze mapping → word detection → context extraction → backend translation → logging. Κάθε κρίκος αυτής της αλυσίδας επηρεάζει την επόμενη. Αν τα OCR boxes δεν αντιστοιχούν σωστά στο rendered PDF, το gaze trigger θα ενεργοποιεί λάθος λέξη. Αν το gaze mapping δεν λαμβάνει υπόψη viewport, scroll ή δεύτερη οθόνη, το σύστημα φαίνεται ανακριβές. Αν η ανίχνευση βασίζεται μόνο σε point matching, ο θόρυβος του eye tracker οδηγεί σε false negatives. Αν το circle mode υλοποιηθεί χωρίς throttling και candidate filtering, το σύστημα επιβαρύνει το browser thread. Αν η μετάφραση γίνεται χωρίς context ή με exposed credentials, η ποιότητα και η ασφάλεια υποβαθμίζονται. Για τον λόγο αυτό, η τελική υλοποίηση συνδυάζει γεωμετρική διόρθωση, gaze uncertainty modeling, context-aware DeepL translation, server-side configuration με .env και session-centric experimental logging.”
